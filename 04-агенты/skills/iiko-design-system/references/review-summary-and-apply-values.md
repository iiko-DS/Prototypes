# Свод по ревью и мостик «ревью → код» (14.09.2026)

Класс задачи: несколько человек (4 дизайнера + 2 ответственных) оценивают паттерны и мобильные
размеры на страницах рекомендаций, а из собранных мнений надо принять общее решение и довести его
до мобильного CSS компонента без ручного переноса чисел.

## Что где лежит

| Путь | Что это | Кто пишет |
|---|---|---|
| `_audit/rec/review/<компонент>.<человек>.json` | личные решения (статусы, комментарии, значения «Правки») | кнопка «В репозиторий» на странице компонента → `POST /__rec-review` в `serve.py` |
| `_audit/rec/review/<компонент>.final.json` | решение встречи (`person: "final"`, `kind: "rec-review-final"`) | кнопка «Сохранить решения» на странице свода |
| `_audit/rec/summary.py` → `_audit/rec/summary.html` | свод: матрица «паттерн × человек» | запуск вручную |
| `_audit/rec/apply-values.py` | принятые значения → мобильный CSS | запуск вручную |
| `iiko-ds-mobile/components/<Папка>_DS/mobile-values.css` | сгенерированный файл значений | `apply-values.py --apply` |
| `iiko-ds-mobile/components/index.css` | `@import "<Папка>_DS/mobile-values.css";` последней строкой | `apply-values.py --apply` |

Разделение намеренное: **один человек — один файл**, поэтому слияние в git без конфликтов; мнения
людей и решение встречи лежат рядом, но в разных файлах, и в код уходят только значения из `.final.json`.
Форматы: личный файл — `version, round, component, componentName, person, savedAt, decisions, seen, edits`;
файл «по всем компонентам» — `version:3, kind:'rec-review-all', components:{<slug>:{decisions, seen, edits}}`.
Ключи `localStorage` на странице: `rec-review-<slug>-v1[:<человек>]`, `rec-seen-…`, `rec-edits-…`.

## Свод: как запускать и что он показывает

```bash
python _audit/rec/summary.py            # собрать _audit/rec/summary.html
python _audit/rec/summary.py --open-hint
```
Открывать через сервер: `http://127.0.0.1:8899/_audit/rec/summary.html` — страница шлёт решения
на тот же origin (`POST /__rec-review`); под `file://` сохранение не работает.

Страница (самодостаточная: данные внутри `<script id="data" type="application/json">`):

- по компоненту — таблица паттернов: столбцы люди, в клетке статус и комментарий человека, у спорных
  строк плашка «расхождение» (`data-split="1"`); ниже таблица правок: значения каждого человека и
  столбец «Итоговое значение»;
- сверху «Кто ответил» (сколько компонентов прислал каждый), внутри компонента — «Не прислали: …»;
- столбец «Решение» (Берём / Отложить / Не берём) и кнопки «Сохранить решения», «Отчёт xls»,
  «только расхождения», «Раскрыть всё»;
- шрифт иконок (`family=Material+Icons`) в шапке обязателен, иначе лигатуры рисуются словами.

Числа на демо-прогоне (три человека × два компонента): Button 3/3 ответили, 22 строки, 3 расхождения
(«Два действия в строку» 2 одобряют / 1 отложить, «Длинная подпись» одобряют / не подходит,
«Высота» 48 / 48 / 52); Dialog 1/3, «не прислали: Боря, Ира»; фильтр «только расхождения» оставляет
1 карточку из 2; xls — 5820 символов, столбцы «Компонент · Что · Тип · <люди> · Решение»;
сохранение — «Сохранено компонентов: 1 (button)» и файл `button.final.json` на диске.

## Мостик: как запускать и что он делает

```bash
python _audit/rec/apply-values.py button.final.json            # предпросмотр: план + unified diff
python _audit/rec/apply-values.py button.final.json --apply     # записать
```
По умолчанию НЕ пишет ничего (это и есть ворота: владелец смотрит diff и говорит «ок»).

Что делает: для каждой правки из `data/<slug>.json` берёт `sel`, шаблон `css` (`min-height:@px`) и
`sync {field, a, b}`; подставляет значения из файла решений; собирает правила
`[data-mode="mobile"] <sel> { … }` (несколько правок с одним селектором сливаются в одно правило);
кладёт их в `mobile-values.css` с шапкой «что утверждено» (источник, автор, дата) и добавляет
`@import` **последней строкой** агрегатора. Ничего другого не трогает — библиотеку `iiko-ds-web` тем более.

Сквозная проверка (обязательна после первой подстановки): после `--apply` открыть страницу компонента и
замерить, что кнопка в теле мобильного экрана стала ожидаемой (было 44 → 48 px при `min-height:48px`
и `padding-top:14px`) — то есть значения из файла решений реально доехали до CSS компонента и до экранов.
После проверки тестовые значения убрать: `rm <Папка>_DS/mobile-values.css` + `git checkout -- iiko-ds-mobile/components/index.css`.

## Капканы

- **Порядок `@import` решает.** Специфичность у слоя и у сгенерированных правил одинаковая
  (`[data-mode="mobile"] .ds-btn--m`), поэтому строка подключения идёт ПОСЛЕДНЕЙ в `components/index.css` —
  иначе значения не перекроют собственные правила слоя.
- **`sync`-формулы применять, но не перебивать явное значение.** `height` 48 → `pad-v = 0.5·v − 10 = 14`
  (в отчёте помечать «формула синхронизации»); если связанное поле задано явно — оставлять его.
- **Префилл только при явном перевесе:** не меньше двух голосов И строгое большинство. Ничья — пусто
  («ничью решает встреча»); один голос — тоже пусто (иначе подсказка одного человека выглядит решением).
- **Сохранять то, что видно в столбце «Решение».** На встрече сохраняются отмеченные статусы и значения
  в полях; пустое не пишется — «пусто» значит «ещё не решили». Иначе в файл попадают непроверенные подсказки.
- **Проверки на входе:** нечисловое значение — пропустить с замечанием (в CSS текст уходить не должен);
  правка, которой нет в `data/<slug>.json` — замечание; селектор, которого нет в CSS компонента —
  предупреждение «проверь глазами» (искать и в мобильном слое, и в `iiko-ds-web/components/*_DS`, и в `modes.css`).
- **Команду отката печатать всегда:** `git checkout -- iiko-ds-mobile/components/index.css && rm -f <мобильный файл>`.
- **Внешнюю запись проверять чтением с диска** (файл `_audit/rec/review/*.json` после POST, `mobile-values.css`
  после `--apply`) — успешный ответ сервера не равен «файл правильный».
- **Тестовые данные не оставлять в репозитории:** демо-файлы решений удалять, `summary.html` собирается заново
  одной командой, сгенерированный `mobile-values.css` — тоже.
- **Многострочный шаблон страницы собирать через токены, а не `%`-формат.** В `summary.py` шаблон с CSS
  (`width:34%`) на `%`-форматировании падал `unsupported format character ';'`; заменено на токены
  `@@AT@@`/`@@PARTS@@` + `.replace()`. Тот же класс ошибок, что `\n` в `%`-шаблоне `build.py`
  (см. капканы в SKILL.md): после сборки страницы гнать `node --check` по её `<script>`.
- **JSON внутри страницы экранировать:** `json.dumps(...).replace("<", "\\u003c")`, иначе `</script>` в данных
  рвёт разметку.
