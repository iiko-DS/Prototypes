# Ревью страниц рекомендаций: шесть человек, свод, решение, патч в CSS (14.09.2026)

Зачем: страницы рекомендаций смотрят 4 дизайнера + до 2 ответственных. Каждый ставит свои
оценки и значения, потом из общей таблицы принимается **одно** решение на компонент: какие
паттерны берём и какие мобильные значения утверждаем. Механизм собран целиком, от браузера
до мобильного CSS компонента — ниже что где лежит и на что наступать не надо.

## Личный слой в localStorage

- Ключи на компонент И на человека: `rec-review-<slug>-v1[:<имя>]`, `rec-seen-<slug>-v1[:<имя>]`,
  `rec-edits-<slug>-v1[:<имя>]`. Имя хранится в `localStorage['rec-person']` и переключается
  только в меню оболочки (`input[data-shell-person]`, `datalist#rec-people`).
- Любая команда из оболочки уходит странице вместе с именем: `postMessage({ds:'review', kind,
  text, person})`; страница при расхождении имени перезагружает свой слой (`loadAll()` + `paint()`
  + сброс `ta.__touched`, иначе в комментарии остаётся текст прошлого человека).
- Один человек = один файл решений → конфликтов слияния в git не бывает в принципе.

## Что на странице компонента

- Статусы паттерна «Одобряем / Отложить / Не подходит» (`accepted/later/rejected`) — в плашке
  описания, справа от заголовка; повторный клик по активному снимает оценку.
- «Свой комментарий» — textarea сразу под строкой «Источники».
- **Кнопок сохранения нет.** Владелец: «У кнопки Сохранить галочка не нужна… можно и вообще без
  галочки», затем «Нужны ли вообще сохранения или они автоматом сохраняются?». Итог: автосохранение
  с паузой 700 мс после ввода и сразу по `blur` (`blur` не всплывает — слушать на перехвате,
  `addEventListener('blur', fn, true)`), рядом тихая пометка «Сохранено» (серый → зелёный на 1,8 с).
- Три уровня сброса, и они не должны пересекаться (владелец на этом настаивал):
  1) «Сбросить» в плашке паттерна — статус + комментарий + отметка «просмотрено» этого паттерна;
  2) «Сбросить оценки паттернов» в меню паттернов — оценки ВСЕХ паттернов компонента, значения
     «Правки» не трогает;
  3) «Сброс правок» в меню компонентов — только значения колонки «Правка» (поля возвращаются
     к `value` из разметки, `#live` чистится), оценки не трогает.
  Раньше был один «Сброс», который чистил всё, — владелец: «Сброс в меню компонентов чистит вообще всё!»

## Прогресс, бейджи, фильтр

- В меню паттернов над списком: «Просмотрено N/M · ✓ · 🕐 · ✕» + кнопка «Сбросить оценки паттернов».
- В меню оболочки: у каждого пункта бейдж (те же три значка + `seen/total`), общий прогресс
  «Решено по N из M компонентов · паттернов просмотрено X из Y (слой <имя>)», фильтр
  «Только не пройденные» (`rec-only-pending`, класс `nav--pending`,
  `.nav--pending .nav__item.is-done:not(.is-active){display:none}`) и «Раскрыть всё».
- Число паттернов на компонент зашивается при сборке: `data-parts="<len(patterns_ru)>"` в кнопке
  меню — иначе прогресс по ДС не посчитать (страница отдаёт только свой компонент).
- Живые бейджи: страница после каждой перерисовки шлёт `{ds:'rec-summary', slug, total, seen,
  accepted, later, rejected}` (троттлинг 400 мс) — оболочка складывает это в `live[slug]` и
  перерисовывает меню.

## Обмен файлами и запись в репозиторий

- Меню JSON: «Скачать по текущему компоненту», «Скачать по всем компонентам» (файл
  `rec-review-all.<имя>.json`, внутри `components: {slug: {decisions, seen, edits}}`),
  «Загрузить решения из файла» (понимает оба вида; кладёт в слой ТЕКУЩЕГО человека, автор файла
  только упоминается в сообщении), «Сброс» (только свой слой).
- «В репозиторий» — по файлу на компонент через POST `/__rec-review`. Сервер (`serve.py`,
  метод `do_POST`) пишет `_audit/rec/review/<компонент>.<человек>.json` и возвращает путь;
  имя файла чистится `safe_name()` (только буквы/цифры/`-`/`_`, длина 48). **Правил `serve.py` —
  перезапусти сервер**: старый процесс отвечает 501 «Unsupported method ('POST')».

## Свод

- `python _audit/rec/summary.py` → `_audit/rec/summary.html` (самодостаточная: данные внутри
  `<script id="data" type="application/json">`, `<` заменён на `\u003c`). Открывать через
  serve.py — иначе решения со встречи некуда сохранить.
- На странице: карточки компонентов с матрицей «паттерн × человек» (в клетке статус и комментарий),
  плашка «расхождение» у строк, где мнения или значения разошлись; правки с значениями каждого
  и полем «Итоговое значение»; шапка «Кто ответил» и «Не прислали: …»; кнопки «Сохранить решения»,
  «Отчёт xls» (клиентский xls как HTML-таблица), фильтр «только расхождения», «Раскрыть всё».
- Подсказка в столбце «Решение» появляется **только при явном перевесе и минимум двух голосах**
  (`n > second && n >= 2`), при ничьей — пусто: ничью решает встреча, а не мода.
- Столбец «Решение» (Берём / Отложить / Не берём) сохраняется тем же POST-ом с
  `person: 'final'` → `_audit/rec/review/<компонент>.final.json`. Сохраняется **то, что видно**:
  отмеченные статусы и непустые поля значений; пустое = «ещё не решили» и не пишется.

## Патч в код

- `python _audit/rec/apply-values.py <файл решений> [--apply]` — по умолчанию только план и diff,
  ничего не пишет. Берёт `edits` из файла решений + машинное описание правки из `data/<slug>.json`
  (`sel`, шаблон `css`, формулу `sync`) и собирает `[data-mode="mobile"] <sel>{…}` в
  `iiko-ds-mobile/components/<Папка>_DS/mobile-values.css`, подключая файл **последней строкой**
  агрегатора `components/index.css` (одинаковая специфичность — решает порядок).
- Связанное поле считается по формуле (`height 48 → pad-v 14`), в CSS уходит согласованная пара.
- Замечания, а не молчание: нечисловое значение, неизвестный `id`, селектор которого нет в CSS
  компонента. Библиотека `iiko-ds-web` не трогается вообще; печатается команда отката.
- Сквозная проверка цепочки (сделана): файл решений → `apply-values.py --apply` → кнопка в теле
  мобильного экрана на странице измерена 48 px при `min-height:48px` и `padding-top:14px`.

## Порядок работы, который владелец принял

встреча → свод по шестерым → ИИ читает свод и предлагает итоговые значения (где спорно —
показывает) → итог кладётся `review/<компонент>.final.json` → `apply-values.py` даёт diff →
«ок» → значения в компоненте. CSS-строки и «что уйдёт в код» на страницах **не показывать**:
владелец решил, что дизайнеру это шум («что под капотом происходит и выводить сразу данные css
кажется лишнее»), отчёта и данных достаточно. Механическая подстановка — скриптом (он не выдумает
несуществующий селектор, всегда даёт diff и откат), а ИИ держать на решениях и на чтении свода.
