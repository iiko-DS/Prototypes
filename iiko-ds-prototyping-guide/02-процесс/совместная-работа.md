# Совместная работа

Как мы вместе работаем с репозиториями. Правила сборки интерфейса из компонентов — в [`../дизайн-система/сборка-из-ДС.md`](../дизайн-система/сборка-из-ДС.md).

Коротко: **`main` — общая база, свои пробы — в своей ветке, в общее — через Pull Request.**

## Ветки и Pull Request

- **`main` — то, чем пользуются все.** Прямо в него не пишем: там должны лежать проверенные вещи.
- **Своя ветка — твоя песочница.** В GitHub Desktop: `Current Branch → New Branch`, имя вида `ivan/badge-fix` (кто / что делает). В ветке можно делать что угодно — остальным это не мешает.
- **Получилось и стоит взять всем** → `Push origin`, затем `Create Pull Request` в `main`. Шаблон описания подставится сам: что меняю, где смотреть, что проверил. Вливать может автор PR или владелец — после обсуждения в комментариях.
- **После слияния ветка удаляется автоматически** (настройка репозитория включена), список веток не зарастает.
- **Перед началом работы** и после чужого PR — обновить базу: `python pull.py`.

Почему нельзя «копить локально, а потом перенести руками»: если держать незакоммиченные правки поверх `main`, первый же `git pull` упрётся в «local changes would be overwritten», и разбирать это придётся по файлам. Ветка — это и есть «локально своё, в общее только важное», только без потери работы.

**Технического запрета писать в `main` нет.** Защита ветки (protected branches) на бесплатном плане доступна только для публичных репозиториев, а у нас все приватные. Значит правило держится договорённостью: соблюдаем сами и напоминаем друг другу.

## Что коммитим, а что нет

- **Коммитим:** данные страниц (`_audit/rec/data/*.json`), технические заметки, CSS компонентов, прототипы, скрипты генератора, тексты этой базы знаний.
- **Не коммитим:** собранные страницы (`components-mobile/prototypes/recommendations/` — это вывод генератора, каждый собирает их у себя), проверочные скриншоты и пробы, секреты (`.env`, `.vscode/mcp.json` с токеном Figma).

## Права и роли

| Кто | Что может |
|---|---|
| Участник организации | читать и клонировать все репозитории (базовые права `read`) |
| Команда `design-system` | плюс писать: свои ветки, push, PR (`write`) |
| Владелец организации | всё: приглашения, права, настройки, репозитории |

Управление: участники — `https://github.com/orgs/iiko-DS/people`, команда — `https://github.com/orgs/iiko-DS/teams/design-system`. Создание новых репозиториев участникам закрыто: новый репозиторий создаёт только владелец, чтобы в организации случайно не появился публичный.

## Как принимаем решения

- Обсуждаем в Pull Request или в issue, а не в личных сообщениях — чтобы решение не потерялось.
- Пришли к решению — **фиксируем его в этой базе знаний** (правило, рецепт, договорённость) и только потом расходимся. Иначе через месяц тот же вопрос всплывёт снова.
- Возражение по существу полезнее молчаливого согласия: если правило мешает — скажи, поправим.

## Ревью компонентов

На страницах рекомендаций (`recommendations/`) есть форма ревью: решение по компоненту сохраняется в `_audit/rec/review/<компонент>.<имя>.json` — по одному файлу на человека. Файлы разных людей не затирают друг друга, их можно коммитить и обсуждать вместе.
