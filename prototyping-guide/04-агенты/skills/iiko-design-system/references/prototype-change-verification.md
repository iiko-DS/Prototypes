# Проверка правок в прототипах — замером, а не «на глаз»

Когда: любая правка страницы-прототипа (KDS, ДС, mobile) — прежде чем отчитываться владельцу.
Скрипт для запуска пробы одной командой: `scripts/probe_page.py`.
**Готовый зонд со постановкой состояния и снимком — `scripts/probe-page.sh --state … --shot …`**
(вклеивает пробу в копию страницы, ставит режим ДО первого `paint()`, снимает PNG; ловушки —
`references/kds-prototype-verification.md`). Сначала брать его, а ручную сборку temp-страниц —
только когда зонда не хватает: 16.09 на ручную сборку ушёл десяток лишних итераций.

## Железное правило: проба и скриншот — только из АКТУАЛЬНОГО файла

- Проба = копия страницы с внедрённым блоком `<pre id="probe"></pre><script>…</script>`,
  лежит в `$LOCALAPPDATA/Temp/p-*.html`.
- Заготовку, собранную раньше (для прошлой правки), НЕ переиспользовать: она показывает старое
  состояние. Реальный инцидент 16.09: владельцу ушёл снимок старой сборки (строка с рамкой по
  периметру, которую давно заменили полосой 4 px слева) → он вернулся с претензией на уже
  исправленное, и пришлось объяснять, что картинка была из устаревшей версии.
- Перед выводом результата убедиться, что замер отражает текущий файл: в выводе должен появиться
  ожидаемый класс/стиль (например `kdsx-row--soon`, `inset 4px 0 0 0`). Если класс не появился —
  сначала проверить, что скрипт-сценарий действительно довёл интерфейс до нужного состояния
  (тихий пропуск шага даёт ложный вывод «всё чисто»).

## Запуск headless Chrome

```bash
"/c/Program Files/Google/Chrome/Application/chrome.exe" --headless --disable-gpu --no-first-run \
  --user-data-dir="C:/Users/<user>/AppData/Local/Temp/chr-<уникальный-суффикс>" \
  --virtual-time-budget=9000 --window-size=1700,1200 \
  --dump-dom "file:///C:/Users/<user>/AppData/Local/Temp/p-<имя>.html" \
  | python -c "import sys,re,html; s=sys.stdin.read(); m=re.search(r'<pre id=\"probe\">(.*?)</pre>', s, re.S); print(html.unescape(m.group(1).strip()) if m else 'нет')"
```

- `--user-data-dir` — уникальный на каждый запуск; один и тот же профиль иногда отдаёт пустой DOM.
- `--virtual-time-budget=9000` — чтобы успел сработать `setTimeout(…, 500–700)` внутри пробы.
- Скриншот: `--screenshot="C:/…/shot.png"` вместо/вместе с `--dump-dom`.
- Пути для нативного Chrome — только `C:/…` (MSYS-пути `/c/…` он не понимает).

## Внутри пробы: как ставить состояние

- Переменные модуля (`elapsedMin`, `pressed`, `screenShop`) через `window.*` НЕДОСТУПНЫ, если скрипт
  обёрнут в IIFE (обычно обёрнут). Состояние ставить только штатными средствами UI.
- Штатные ручки: чипы времени (`.chip` со текстом `10 мин` / `20 мин`), галочка `[data-time-chk]`,
  табы `[data-vtab]`, цех на экране `[data-scrshop]`, вариант на экране `[data-scrvar]`,
  кнопки нажатия `[data-press]`, сброс `[data-reset]`.
- Порядок важен: таб/цех → нажатие блюда (иначе «отобьёт» не тот цех) → чип времени.
- Не искать элемент «на глаз»: `[].filter.call(document.querySelectorAll('.chip'), x =>
  x.textContent.trim()==='20 мин')[0]` и обязательно проверить, что найден (иначе шаг молча пропущен).
- Псевдоэлементы проверять отдельно: `getComputedStyle(el,'::after')`.

## Приём: свип «нет ли рамки-линии в цвете просрочки»

Применялся, чтобы доказать правило «просрочка = только полоса 4 px слева»:

```js
var WARN=['rgb(255, 171, 64)','rgb(255, 82, 82)'];
function warn(s){ return s && WARN.some(function(c){ return s.indexOf(c)>=0; }); }
// по всем элементам проверяемой области:
//   border-top/right/bottom/left с цветом из WARN и шириной > 0  → линия/рамка
//   outline с цветом из WARN                                     → обводка
//   box-shadow с цветом из WARN, кроме `rgb(...) 4px 0px 0px 0px inset` (ожидаемая левая полоса)
//                                                                 → линия
```

Результат «0 элементов» — это тоже результат, его пишем владельцу числом, отдельно по каждой
области (панели цехов, режим «по блюдам», общий экран).

## Сверка с макетом Figma: замер, а не «на глаз»

Владелец присылает ссылку на узел (`…?node-id=9293-16037`) и говорит «у нас это выглядит вот так» —
это задание: привести наш экран к макету ПО ЧИСЛАМ. Инцидент 16.09: «Отрисовал ты не очень хорошо,
есть косяки, например с отступами» — паддинги были взяты «на глаз». Владелец проверяет отступы
придирчиво, поэтому мерить обязательно.

- Снять узел: Dev Mode MCP (`get_metadata` + `get_screenshot`; в вызове node-id через `:`,
  в ссылке — через `-`). Кириллица в именах слоёв приходит битой (U+FFFD) даже с `--json-out`,
  поэтому подписи и тексты читать со СКРИНШОТА, а из метадаты брать только габариты и вложенность.
- Скриншот узла Figma = кадр в масштабе: 1280 → 1024, то есть ×0.8. Пиксельные замеры делить на 0.8.
- Мерить макет пиксельно (numpy, по столбцу/строке искать цвета фона). Тёмная тема КДС: `#333333` —
  экран вне списка, `#121212` — фон списка и левая колонка строки, `#212121` — плашка блока с блюдом,
  `#424242` — кнопка. Так видно то, чего глазом не видно: например, что заливка `#212121` есть ТОЛЬКО
  у блока блюда, а строка и мета прозрачные (у нас заливка была на всю строку — это и был «косяк»).
- Наш экран мерить по DOM, а не по снимку: `offsetWidth/offsetHeight` (без масштаба сцены) и
  `getBoundingClientRect()` — для взаимных отступов. Важно: `getBoundingClientRect()` на сцене с
  `transform: scale()` (режим «fit» общего экрана) отдаёт масштабированные числа — по ним не сверять.
- Готовый разбор анатомии строки «по блюдам» (узел Figma 9293:16037) и таблица «макет → было → стало» —
  в `references/kds-sketches-owner-rules.md`.

Ловушки, на которых уже спотыкались:

- `--screenshot` в headless снимает состояние на момент `load`, ДО `setTimeout`-проб. Если нужный режим
  ставится отложенно, снимок будет не тот. Правильно: собрать temp-страницу, где состояние выставлено
  СИНХРОННО (правкой констант в копии файла: `uiMode='dishes'`, активная секция `data-vpanel`,
  `screenVariant`, включённое время, `pressed`), и снимать её.
- `color:var(--x)` молча не применяется, если переменной нет в этой области (в панелях нет
  `--kds-text`) → цвет наследуется от страницы и текст становится нечитаемым. Проверять
  `getComputedStyle(el).color` числом, а не «должно быть белым».
- Фон нужной высоты = фон по `content-box` (`background-clip:content-box`) при паддинге 8; иначе
  заливка растягивается на всю строку и плашка перестаёт совпадать с макетом.

## Проверка JS

Извлечь последний `<script>` из АКТУАЛЬНОГО файла → `$LOCALAPPDATA/Temp/ms-checkNN.js` →
`node --check` (единственная надёжная проверка синтаксиса до рендера).

## Отчёт владельцу

- Числами: сколько элементов/px и где именно; «0» писать явно.
- Если правка не понадобилась (поведение уже верное) — сказать прямо и приложить свежий замер:
  «проверил замером — уже так», без выдумывания изменений ради изменения.
- «Убери X» владелец читает буквально и во всех местах сразу: убрал в одном варианте — считай, не
  убрал (инцидент 16.09: «Ты не везде удалил» про строки сброса). После такой правки проверять
  СЧЁТОМ по DOM (сколько кнопок/строк осталось и сколько ожидается) и писать это число в отчёте.
- Правки, меняющие разметку блока, владелец принимает постепенно: сначала сказать, что даст и как
  будет выглядеть, дождаться «делай». Но если он сам показал макет/скриншот — собирать и показывать
  результат нажатиями (живой экран), а не страницу-отчёт таблицами.
- Двусмысленная формулировка → сделать однозначную часть, затем ОДИН короткий вопрос про спорное;
  свои улучшения и «заодно» владелец читает как саботаж.
- Скриншоты — только в папку макетов задачи (`Prototypes/KDS/_kds-*.png`), не на Рабочий стол;
  устаревшие снимки удалять, чтобы они не путали (одна картинка старого поведения стоила отдельного разбора).
