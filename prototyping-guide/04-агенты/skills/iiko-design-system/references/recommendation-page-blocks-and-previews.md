# Пайплайн `out/` и блоки страниц рекомендаций

Класс задачи: правки страниц `components-mobile/prototypes/recommendations/` приходят
заготовками от исполнителей, сводятся в данные и собираются генератором. Здесь — как это
устроено, какие правила владельца закреплены и как проверять результат.

## Поток данных

```
_audit/rec/out/edits/<slug>.json      → changes[].edit, changes[].mobile
_audit/rec/out/previews/<slug>.json   → preview_html   (блок «На экране»)
_audit/rec/out/platforms/<slug>.json  → platform_notes_ru, logic_ru
_audit/rec/out/patterns/<slug>.json   → patterns_ru    (блок «Примерные паттерны поведения»)
                ↓  python apply_out.py [--build]
_audit/rec/data/<slug>.json           → единственный источник страниц
                ↓  python build.py
components-mobile/prototypes/recommendations/{index.html,<slug>.html} + rec.css
```

- `apply_out.py` **заменяет** поля целиком: `previews` перезаписывает `preview_html`,
  `patterns` — массив `patterns_ru` вместе с примерами. Это не «дополнение», а замена.
- `rec.css` **пишет `build.py`** из своей константы `CSS = """…"""` — правка этого файла
  выглядит удавшейся и исчезает при следующей сборке. Стили добавлять в `build.py`.
- Компоненты (`components-web`) и `modes.css` генератор не трогает — все демонстрационные
  правила живут на странице.

## Правила владельца (сформулированы по ходу работы, нарушать нельзя)

1. **Ничего не менять без прямого «да».** Скрин/замечание ≠ задание. Перед правкой — одна строка
   «файл + элемент + что станет», ждать ответа; после — замер только того, о чём просили;
   найденное рядом — списком, не чинить; двусмысленная фраза — один короткий вопрос до правки.
2. **Не вливать пачку сгенерированных файлов вслепую.** Влил 37 превью разом, не открыв ни одного, —
   на страницах «слетели экраны», владелец: «Где примеры компонентов… Там ни одной кнопки нет».
   Порядок: открыть ОДИН файл → показать одну страницу → «да» → вливать остальное.
3. **Не подменять пересборку копированием.** Расхождение двух экранов «лечится» пересборкой превью,
   а не копированием левого экрана в правый: текстовые строки в шторке кнопками не станут.
4. **Порядок блоков на странице:** `На экране` → `Примерные паттерны поведения` → `Что меняется на мобиле`
   → `Почему так` → `Итог` (блок паттернов поднят выше «Что меняется» по прямой просьбе).

## Инварианты блока «На экране» (два экрана)

- Ровно два `phones__item`.
- **Один и тот же интерфейс**: шапка (`phone__title`), тело, шторка (`phone__sheet` с тем же
  заголовком/текстом) совпадают; отличаются только подписи `phone__caption` под экранами.
- Компонент виден **и в теле, и в шторке** — настоящей разметкой ДС, не строками `phone__row`
  вместо компонента.
- Правый экран помечает **сборка** (`data-preview="edit"`), в него пишутся правки полей «Что|Правка»;
  левый остаётся со значениями как рекомендовано. Проверка: ввести в поле число и убедиться, что
  на правом экране значение изменилось, а на левом нет.
- Если контейнер примера — не `.panel`/`.phone` (например `.pat__phone` в табах), правила каркаса
  для него надо скопировать (см. SKILL.md, «Новый блок получает правила каркаса только явно»).

## Паттерны внутри блока «На экране» (меню + текст под экранами)

Отдельного блока «Примерные паттерны поведения» с табами больше нет: паттерны переехали внутрь
блока «На экране» (13–14.09.2026, по прямой просьбе владельца). Прежняя схема (табы
`ds-tabs--lvl2` со стрелками и плашкой-превью `.pat__ex`) — история; если увидишь её на странице,
значит страница не пересобрана.

- Слева от экранов — вертикальное меню `.screens__item` (первый пункт «Основные» = дефолтные кнопки,
  текста под экранами нет); у меню своя прокрутка, если не влезает в высоту.
- Пункт меню = паттерн: при клике кнопки из его `example_html` подставляются в слоты
  `data-buttons="screen"` / `data-buttons="sheet"` — одинаково на двух экранах; текст паттерна
  показывается **под экранами** (`[data-note]`).
- Текст начинается **заголовком паттерна** (`h3.screens__note-title`, правило в `build.py`): «Два
  действия в строку» → подпись к примеру (`example_ru`) → пункты → «Источники: …». Без заголовка
  непонятно, к какому пункту меню относится то, что читаешь.
- В пунктах паттерна осталось **два** пункта: «Что делают системы» вырезано из всех страниц
  («Это лишнее, там все равно по английски и ничего не понятно») — на страницу не возвращать.
- Стрелки табов и плашка `.pat__ex` не нужны: пример виден на самих экранах.
- Поля паттерна: `title`, `items` (три пункта с префиксами «Что происходит: », «Что делают системы: »,
  «Что делать нам: »), `src` (названия и адреса источников) и **пример**: `example_html` (разметка ДС)
  + `example_ru` (одна честная фраза, что показано).
- Примеры-кнопки из этого блока (эталон): две кнопки в строку · главное + «⋯» · подпись переносится
  на вторую строку · на всю ширину · иконка с пунктирной зоной 48 × 48 · недоступная кнопка на время
  запроса.
- **Кнопки в примерах паттернов подчиняются мобильному заполнению строки** (14.09.2026): одна кнопка
  в слоте — на всю строку (`.btnbox > .ds-btn{width:100%}`), строка из нескольких — поровну
  (`.pat__phone-row .ds-btn{flex:1 1 0}`; было `1 1 auto` — тянуло на всю ширину, но неравномерно,
  121 / 90 / 99,7). Замеры после правки при слоте 327 px: «Два действия в строку» 159,5 + 159,5,
  «Один главный призыв на странице» 103,7 ×3, «Разрушительное действие не главное» 159,5 + 159,5,
  «Третье и четвёртое действие не влезают» 279 + 40 (иконка), «Кнопка-иконка без подписи»
  40 (иконка) + 327. Инлайновые `style="flex:1 1 auto"` в `example_html` — убирать: это то же правило,
  но мимо ДС (так было в «Кнопка исчезла при свайпе шторки»: 172,4 + 146,6 → 159,5 + 159,5).
  Сознательное исключение, не выравнивать: только кнопки S/XS в демо тач-зоны (`.pat__hit`, по содержимому,
  53 + 56,3). Узкий контейнер `.pat__narrow` 180 px исключением больше не считается — обе «длинные подписи»
  переведены на полную ширину (см. ниже).

### Пример паттерна обязан показывать то, о чём паттерн (14.09.2026)

Владелец: «Длинная подпись переносится — текст на кнопке переносится, но сама кнопка не растянута на всю
ширину строчки. Она одна стоит в строке и должна растягиваться по ширине. И таких примеров ещё есть,
нужно такие баги подчистить».

- Обе «длинные подписи» больше не сидят в узком `.pat__narrow` 180 px. Новая обёртка каркаса:
  `.pat__wrap{width:100%;display:flex}` + `.pat__wrap .ds-btn{width:100%;height:auto;min-height:44px;
  padding:12px 16px;white-space:normal}` + `.pat__wrap .ds-btn__label{white-space:normal;line-height:20px;
  text-align:center}`. В данных `.pat__narrow` не осталось (само правило CSS оставили — им могут
  пользоваться другие компоненты).
- **Прежде чем объявлять демо переноса рабочим, замерить ширину подписи в одну строку** и сравнить с
  доступной полосой. Подпись «Сохранить и отправить на кухню» — 217 px при 14 px и ≈265 px при 16 px,
  а доступно 327 − 32 = 295 px: на всю ширину она НЕ переносится. Поэтому в примере подпись удлинена до
  «Сохранить и отправить **заказ** на кухню» (≈323 px) — и та же формулировка синхронно поправлена в
  цитатах внутри `items`/`example_ru` этого паттерна, иначе текст противоречит примеру.
- После правки: кнопка 327 × 66, подпись в две строки; в прогоне по 20 паттернам обе «длинные подписи»
  стоят как `327 (2 строки)`, остальные — 327 / 160 + 160 / 104 ×3 / 279 + 40 (иконка) / 40 + 327.
- Общий критерий: пример адекватен, только если он показывает то, что утверждает его заголовок. Если
  кнопка не растянута, перенос не виден или подпись усечена — это баг примера, а не косметика.

### Переполнение примера: содержимое не выходит за рамку кнопки (14.09.2026)

Владелец: «Один главный призыв на странице — у нас 3 кнопки в строчке. Первая кнопка с иконкой и
надписью сохранить не везает. Она ушла за рамки кнопки. Такое не может быть. Применяй свои же паттерны
что описаны. Если что-то не влезает, значит уходит в три точки или ещё что-то.»

- Причина: в строке три кнопки (`flex:1 1 0` → по 104 px), а главной после добавления иконки нужно
  113 px (иконка 20 + gap 8 + подпись 85) — подпись вылезла за рамку на 43 px. Иконки я добавил сам на
  предыдущем шаге (правило «кнопки в макете разных видов»), а строку под них не переложил.
- **Как проверять** (после любой правки содержимого примеров — иконки, слова в подписи): сравнить сумму
  ширин детей кнопки (+ `gap`) с её контентной областью и отдельно — не выходит ли прямоугольник
  ребёнка за рамку кнопки:

```js
[].forEach.call(d.querySelectorAll('[data-buttons] .ds-btn'), function (b) {
  var cs = wi.getComputedStyle(b), pad = parseFloat(cs.paddingLeft) + parseFloat(cs.paddingRight);
  var inner = 0, gap = parseFloat(cs.gap) || 0;
  [].forEach.call(b.children, function (c) { inner += c.getBoundingClientRect().width; });
  var out = [].some.call(b.children, function (c) {          // выход за рамку — то, что видит владелец
    var cr = c.getBoundingClientRect(), br = b.getBoundingClientRect();
    return cr.right > br.right + 0.5 || cr.left < br.left - 0.5;
  });
  if (inner + gap > b.clientWidth - pad + 0.5 || out) console.log(b.textContent.trim(), 'переполнение', out);
});
```

- **Как чинить — по своим же паттернам, а не подгонкой:** главное действие уходит отдельной строкой на
  всю ширину, второстепенные делят строку ниже; либо лишнее действие убирается под «⋯». Пример «Один
  главный призыв на странице» переложен так: `.pat__phone` (колонка) с залитой «✓ Сохранить» и вложенным
  `.pat__phone-row` с «Далее» + «Отмена». Замер после правки: «✓ Сохранить» 327 × 44, «Далее» 83 × 44,
  «Отмена» 94 × 44 — подписи внутри рамок у всех трёх. Уменьшать кегль и усекать подпись нельзя: это ровно
  то, против чего написаны паттерны «Длинная подпись» и «Один главный призыв на странице».
- **Прогонять проверку по всем паттернам, а не смотреть один.** В прогоне по 20 паттернам реальное
  переполнение было одно (этот случай); строки вида «нужно 301 / есть 293» (длинные подписи) и «23 / 19»
  (S/XS) даёт бокс подписи `.ds-btn__label` с `display:inline-flex` — он на пару пикселей шире контентной
  области, но остаётся внутри рамки (padding 16 px его съедает). Критерий дефекта — **выход за рамку**, а
  не «нужно > есть».
- Заодно `.pat__wrap .ds-btn__label` получил `max-width:100%`, чтобы бокс переносящейся подписи не
  выходил за контентную область.

### Дубли паттернов и сверка «пример ↔ текст» (14.09.2026)

Владелец: «Убери дубли паттернов что повторяются. Они там есть. Например Длинная подпись или кнопка на
всю ширину. И Проверь паттерны просил чтобы они реально отображали в интерфейсе то что написано текстом.
Если написано Загрузка вместо двойного нажатия — то и на экранах нужно отобразить это. Кажется у кнопки
должен быть лоадер!»

**Признак дубля:** разные заголовки, но одно правило, одна цитата источника и один и тот же `example_html`.
Так ушли 4 из 20 (`patterns_ru` → 16):

| Удалён | Дубль чего | Почему |
|---|---|---|
| «Длинная подпись переносится» | «Длинная подпись» | тот же Carbon-абзац и тот же пример |
| «Кнопка на всю ширину экрана» | «Кнопка на всю ширину» | тот же ряд [Отмена] + [✓ Сохранить заказ] |
| «Одна primary-кнопка на страницу» | «Один главный призыв на странице» | одно правило: одна заливка на экран |
| «Нажатие не сработало или нажали дважды» | «Загрузка вместо двойного нажатия» | то же правило про двойной тап |

- Ценное из дубля **переносить**, а не терять: из «Нажатие не сработало…» в оставшийся паттерн ушла
  формулировка «подпись на время загрузки не подменять — иначе кнопка меняет ширину и «прыгает»».
- Заголовок приводить к стилю из текста и примера: «Warning-кнопка только для необратимого» →
  «Negative-кнопка только для необратимого» (в тексте и в разметке `negative`, а не `warning`).
- 16 паттернов `checks/check-patch.py` пропускает — замечаний по `PAT-COUNT` нет.

**Сверка примеров с текстом** (проходить по каждому паттерну: видно ли на экранах то, что утверждает
заголовок):

- «Загрузка вместо двойного нажатия» — был просто второй `disabled`-дубль кнопки. Теперь в примере две
  кнопки: обычная «Отправить» и **та же кнопка в состоянии загрузки** — `disabled` + спиннер внутри,
  подпись не подменяется. В ДС состояния загрузки нет вовсе (ни правила у Button, ни отдельного
  Spinner/Progress), поэтому вращение — правило каркаса:

```css
@keyframes pat-spin{to{transform:rotate(360deg)}}
.pat__spin{animation:pat-spin .9s linear infinite}
```

- ⛔ **`progress_activity` не рендерится: это имя из Material Symbols, а страницы подключают классический
  `https://fonts.googleapis.com/icon?family=Material+Icons`.** Лигатура не срастается и рисуется
  literal-текстом (~140 px) — подпись выдавило за рамку кнопки, а на статичном скриншоте это выглядело
  «какой-то иконкой». Ловится замером ширины глифа: 20 px у лигатуры против 140 px у текста. Для
  спиннера брать `autorenew` (классический набор); сомнительное имя иконки проверять замером, а не глазами
  по кадру.
- «Кнопка ушла под клавиатуру» — клавиатуры в примере не было. Добавлена блоками каркаса (элемент
  системы, не ДС, поэтому цвета простые):

```css
.pat__keyboard{background:#e8eaef;border-radius:8px;padding:6px;display:flex;flex-direction:column;gap:4px}
.pat__keyboard-row{display:flex;gap:4px}
.pat__key{flex:1 1 0;height:22px;background:#fff;border-radius:4px}
```

- **Пример, который уезжает под шторку, владелец не увидит.** Клавиатура в теле экрана оказалась закрыта
  открытой шторкой (тело кончается там, где начинается шторка) — пришлось решать, куда её ставить.
  В `screens_card()` добавлена возможность дать шторке свой пример:
  `ex_sheet = g.get("example_html_sheet") or ex` — ключ `example_html_sheet` для случаев, когда слоту
  шторки нужен другой состав (для клавиатуры он в итоге не понадобился: пример идёт и в шторку, и
  клавиатура видна именно там).
- «Кнопка серая и не нажимается» — проверять, а не ждать жалобы: недоступная кнопка в примере уже была
  (`disabled` на «Печать пречека»), замер показал 1 такую кнопку, менять нечего.
- Массовая правка содержимого примеров (иконки, слова в подписях) и раскладка строки делаются **вместе**:
  именно иконки, добавленные в главные кнопки, дали переполнение в строке из трёх (см. раздел выше).
  После каждой такой правки — прогон проверки переполнения по всем паттернам и проба по обоим слотам.

### Компонент в шторке: поле комментария (`ds-textarea`) — 14.09.2026

Владелец: «Поправь нормально выведи комментарий компонент в шторке». В макете поле рисовалось
браузерной коробкой; причины все в каркасе, а не в разметке:

1. `.ds-textarea{width:250px}` — ширина задана числом в ДС (как диалог 500 px и снекбар 370 px) → не растягивается.
2. `.ds-textarea__input-content` без `flex` → сжимается по содержимому поля.
3. У `.ds-textarea__field` в библиотеке **нет ни одного правила** (в отличие от `.ds-input__field` с
   `border:none; width:100%`): браузер рисует рамку `1px rgb(118,118,118)`, белый фон и ширину по `cols` ≈ 175 px.

Каркас (`build.py`; библиотеку не трогаем):

```css
.phone__screen .ds-textarea{width:100%}
.phone__screen .ds-textarea__input-content{flex:1 1 auto;min-width:0}
.phone__screen .ds-textarea__field{width:100%;box-sizing:border-box;border:0;background:none;
                                   padding:0;font:inherit;color:inherit}
```

Замер до → после: `ds-textarea` 250×126 → 327×104, рамка поля 250 → 327, `textarea` 168×78 с рамкой →
293×72 без рамки и фона, шрифт 16 px, плейсхолдер «Комментарий для заказа» на месте. Копии правил `.panel`
теперь раскладываются и на `.phone__screen` (раньше только на `.pat__panel`) — чтобы компоненты ДС в теле
и в шторке не тащили артефакты автогена.

### Метка тапа — кружок 44 px поверх кнопки (14.09.2026)

Владелец: «На мобиле нужно показать не курсор, а кружок который имитирует тач. Размер наверное
44 px, кажется усредненное значение для усреднённого пальца». Правило в `build.py` (каркас страниц):

```css
.pat__hit{position:relative;display:inline-flex;margin:0 10px}
.pat__hit::before{content:"";position:absolute;left:50%;top:50%;width:44px;height:44px;
  transform:translate(-50%,-50%);border-radius:50%;pointer-events:none;z-index:2;
  background:color-mix(in srgb,var(--ds-palette-accent-500,#448AFF) 22%,transparent)}
```

- Было: пунктирный квадрат 48 × 48 со скруглением 8 px — читается как «курсор/цель», а не палец.
- **Рисовать поверх (`z-index: 2`) обязательно.** На мобиле все размеры кнопки — 44 px высоты
  (`Button_DS/button-touch.css`: M/S/XS = 44); замер кнопок в примерах: 53 × 44 и 56 × 44. Маркер,
  нарисованный под кнопкой (`z-index: auto`), не виден вовсе — первый заход выглядел пустым,
  и это подтвердилось только зумом скриншота.
- 44 px обоснован: усреднённая подушечка пальца и минимум хит-региона Apple HIG («at least 44x44 pt»).
  Невидимая зона нажатия 48 px остаётся слоем CSS (`button-touch.css`) — кружок это показ, не зона.
- Метка стоит там, где на мобиле показывают само нажатие (обёртка `.pat__hit` в `example_html`);
  сейчас это 9 компонентов: button, button-icon, banners, badge, icon-size, hint-tooltip, chips,
  stepper, tree. Разметку менять не пришлось — правило лежит в общем `rec.css`, поэтому подтягивается
  всеми страницами сразу (пересобирать страницы под это не нужно).
- Если владелец попросит кружок и в других демо (нажатая кнопка в «Нажатие не сработало»,
  «Загрузка вместо двойного нажатия») — это правка разметки примера плюс обёртка `.pat__hit`, а не CSS.

### Затемнение экрана под шторкой (14.09.2026)

Владелец: «Если у нас выводится шторка, значит основной экран чуть затемняется». В первой итерации
слой затемнения я снял (в рендере узла Figma подложка визуально не читалась) — теперь он вернулся и это
**компонент ДС**:

```html
<!-- внутри .phone__screen, перед шторкой -->
<div class="ds-backdrop phone__scrim"></div>
<div class="phone__sheet">…</div>
```

```css
.phone__scrim{position:absolute;left:0;right:0;top:0;bottom:0;
              background:var(--ds-color-backdrop-background,#333333);opacity:.32}
```

- **32 % — платформенное значение** (MD3 scrim и Angular `rgba(0, 0, 0, 0.32)`; то же закреплено на
  странице рекомендаций Backdrop). У самого `.ds-backdrop` в ДС задан только цвет — прозрачность
  ставит каркас; своё значение (не 32 %) не выдумывать.
- **Порядок в DOM обязателен:** затемнение идёт до `.phone__sheet`; обе позиции `absolute` без `z-index`,
  поэтому порядок решает — иначе приглушится и шторка.
- Замер: затемнение 359 × 720 = ровно площадь экрана, позиция совпадает с экраном (369,660 / 764,660),
  фон `rgb(51, 51, 51)`, `opacity 0.32`, порядок в DOM 4 против 5 у шторки — на обоих экранах.
- Проверять глазами скриншота: «экран приглушён, шторка светлая». Слой ставится в `preview_html`, то есть
  виден и в дефолте, и во всех паттернах (шторка в макете всегда открыта).

### Кнопки в макете — разных видов (14.09.2026)

Владелец: «Сейчас в интерфейсе все кнопки одинаковые, только текст. А должны быть разные. И просто текст,
и текст + иконка и просто иконка». Речь про **слоты**: при выбранном паттерне в них попадали две
однотипные текстовые кнопки, и экран выглядел однородным.

- В дефолтном экране три вида есть всегда: «только иконка» — `ds-btn-icon` в шапке (`←`, `⋮`), круглая
  `ds-search--xs`, иконки в карточке (`⌄`, `✕`); «текст + иконка» — «＋ Добавить продукт» и
  «✓ Сохранить»; «только текст» — «Отменить». Замер по DOM левого экрана:
  `иконка, иконка, текст+иконка, иконка, иконка, иконка, текст, текст+иконка`.
- В примерах паттернов иконку получает **главная (залитая) кнопка** по смыслу подписи: Сохранить/
  Применить → `check`, Отправить → `send`, Удалить → `delete`, Обновить → `refresh`, Создать/Добавить →
  `add`, Далее → `chevron_right` (в конец подписи). Проставлялось скриптом по `patterns_ru`: иконку
  получили 15 паттернов, текстовая кнопка осталась рядом — набор смешанный («текст+иконка, текст»).
- Текстовыми оставлены сознательно: «Длинная подпись» и «Длинная подпись переносится» (иконка отнимает
  ширину у подписи, которая должна переноситься) и «Зона нажатия минимум 44 pt» (там S/XS с меткой зоны).
  Тексты паттернов это не ломает — они описывают стиль (заливка/обводка/текст), а не наличие иконки.
- Разметка строго слотом ДС: `<span class="ds-btn__icon material-icons">check</span>` рядом с
  `ds-btn__label` (иконка слева; `chevron_right` — справа от подписи).

### Прогон всех паттернов одной пробой

Проверять заполнение строки и заголовки у **всех** пунктов меню, а не у одного: страница-проба в
`_audit/rec/checks/` с `iframe` на страницу компонента, затем в цикле
`d.querySelectorAll('.screens__item')` → `.click()` → `await wait(200…800)` → замер
`[data-buttons="screen"] .ds-btn` и `[data-buttons="sheet"] .ds-btn`, `.ds-btn-group`,
заголовка `[data-note] .screens__note-title` и числа `li`; вывод — в `<pre id="out">`, чтение —
`--dump-dom`. Так получена таблица по 20 паттернам (159,5 + 159,5 · 103,7 ×3 · 327 · исключения)
и подтверждены заголовки у каждого. Клик без ожидания даёт пустые замеры — после `.click()` ждать.

Два капкана этих проб (оба ловил на этой задаче):

- **Пункт меню искать по тексту, а не по индексу.** В меню первым идёт «Основные», поэтому индекс
  пункта = индекс в `patterns_ru` + 1: `it[9]` — это паттерн с индексом 8, а не 9 («Зона нажатия»
  вместо «Длинной подписи»). Надёжно:
  `[].filter.call(it, x => x.textContent.trim() === 'Длинная подпись переносится')[0].click()`.
- **Проба молчит (`<pre>` остался с «…») — сначала проверить, что `run()` действительно вызван.**
  `async function run(){…}` без `run().catch(…)` не даёт ни строк, ни ошибки; выглядит как «страница
  не загрузилась». При отладке переноса подписи я потерял на этом прогон.
- Скриншот интерактивного состояния — отдельной пробой, которая сама кликает пункт меню или шлёт
  `PointerEvent` (`pointermove`/`pointerdown`/`pointerleave`), и **отдельным** запуском Chrome с
  `--screenshot` (в одном запуске с `--dump-dom` кадр снимается раньше, чем проба досчитает).

## Проверка: `checks/check-patch.py`

Запуск по одному или всем слагам: `python checks/check-patch.py` (пустой список = все `data/*.json`).
Скрипт читает заготовки из `out/`, а если их нет — данные. Правила:

- `PREV-2SCREEN` — не два экрана; `PREV-BALANCE` — разметка не сходится;
- `PREV-CLASS` — класс не из CSS ДС; `PREV-NOCOMP` — компонента нет на экране;
- `PREV-INTERFACE` — разные шапки или шторки; `PREV-SAME` — интерфейс двух экранов различается
  больше, чем подписями;
- `PAT-COUNT` (3–6), `PAT-TITLE`, `PAT-ITEMS`, `PAT-SRC`;
- `EX-MISSING` / `EX-NOTE` / `EX-BALANCE` / `EX-CLASS` — пример к паттерну;
- `ROW`, `MOBILE-NONUM`, `SEL`, `CSS`, `DUP-ID`, `STILL-TAKZHE` — строки таблицы «Что меняется» и поля «Правка».

**Капкан при сравнении экранов.** Превью разбирается по `<div class="phones__item">`; в последней
части на конце остаётся ещё закрытие обёртки `.phones`. Снимать его ДО сравнения (и до удаления
подписей), иначе «одинаковые» экраны никогда не сравняются. В `_one()` не использовать `\s`-экранирование
через двойной слэш в строке патча — регулярка молча не срабатывает; надёжнее `" ".join(markup.split())`.

## Замеры и скриншоты (headless)

- Браузер — headless Chrome из терминала: `--headless=new --disable-gpu --no-sandbox --user-data-dir=<свежий>`,
  `--dump-dom` для замеров, `--screenshot=<png> --window-size=W,H` для картинки; обрезка — PIL.
- Замеры внутри страницы делать **страницей-обёрткой** в `_audit/rec/checks/` (тот же origin — сервер 8899),
  внутри `iframe` на нужную страницу, результат печатать в `<pre id="out">` и читать `--dump-dom`.
  Так проверялись: геометрия карточки, поведение стрелок табов, одинаковость экранов, 38 страниц за один прогон.
- Нативным инструментам (`curl`, `git`, `chrome.exe`) давать пути вида `C:/…`. MSYS-путь `/c/…`
  не транслируется: `git -C /c/…` отвечает `fatal: cannot change to`, а `curl -o /c/…` пишет 0 байт
  при коде ответа 200 — ошибка выглядит как «страница пустая».
