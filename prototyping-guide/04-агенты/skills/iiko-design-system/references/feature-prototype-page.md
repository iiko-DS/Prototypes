# Прототип новой доработки по описанию задачи (Prototypes)

Класс задачи: «Создай прототип по описанию задачи» — приходит текстовое описание доработки
(колонка в форме оплаты, модальное окно, состояния загрузки/пустоты, карточка заказа) и требование
«примени нашу дизайн систему и инструкцию по созданию прототипов». Источника-макета может НЕ быть:
ссылка на спеку из трекера часто не доезжает.

Проверено 15.09.2026 на `Prototypes/callcenter-noncash-payment.html` (страницы в репозитории уже нет)
(Веб-КЦ: безналичная оплата на контрагента, 11 состояний, ~51 КБ, один файл).

## 1. Что именно собирать

**Одна страница на всю доработку со переключателем состояний** — это формат, который владелец уже
принял в КДС (`KDS/ux-proposals.html`). Не разносить состояния по файлам: «все состояния проработаны»
он проверяет, кликая по списку, а не открывая 10 страниц.

Каркас файла:

```
<head>  font.css → tokens.css → styles.css → components/index.css
        → (Radio/Checkbox файлы, если используются — их нет в агрегаторе)
        → fixes.css → app-header/app-header.css → app-sidenav/app-sidenav.css
        → Material Icons → свой <style>
<body>
  .modes-bar   — шапка ревью: название доработки, «Подсказки ДС · N», <select> состояний, ← →, счётчик
  .hints       — пробелы ДС, найденные при сборке (показ кнопкой в шапке или ?hints=1)
  .note        — что на экране в выбранном состоянии + «Почему так»
  .view > .panel#panel[data-mode="desktop"] > .frame#frame   ← сюда рендерится состояние
  скрипты: app-header.js, app-sidenav.js, свой скрипт
```

Контракт `app-header.js` / `app-sidenav.js`: оба вставляются в `.panel` **перед** `.frame`
(`sidenav` — `insertBefore(nav, frame)`, шапка — первым ребёнком панели), сами себя они от повторной
вставки защищают (`panel.querySelector('.apph')`). Значит перерисовывать можно только `#frame` —
шапка и рельса остаются.

Обязательный комментарий в `<head>`: источник («подробное описание доработки», дословные подписи
из задачи), что собрано пунктами, «ОТКУДА ЧТО ВЗЯТО» (компоненты ДС, каркас по образцу конкретного
прототипа, ассеты app-header/app-sidenav), честная строка про макет-источник: «макет-источник и спека
не приложены, данные экрана — правдоподобные данные прототипа». Так же делают все страницы `figma-*`.

## 2. Переключатель состояний

```js
var SCEN = [ {id, group, title, panel:{...}, dialog:{...}, payments:[...], what:'…', why:'…'}, … ];
var VIEW = { id, query, cpId };
```

- Меню строится из `SCEN` (`<select>` в шапке), состояние живёт в адресе: `?state=<id>` — прямая
  ссылка, `?ui=0` — чистый кадр без обвязки ревью, `history.replaceState` (не `location.hash` — иначе
  каждый переход пишет запись в историю).
- Стрелки ← → переключают состояния, но игнорируют клавиши, когда фокус в `INPUT`/`SELECT`.
- `.note` собирается из полей состояния: группа, заголовок, «Что на экране», «Почему так». Тексты
  требований брать **дословно** из задачи (названия кнопок, «Выберите контрагента», «Нет доступных
  контрагентов. Создайте контрагента в iikoOffice (Сети)») — владелец сверяет формулировки буквально.
- Поля состояния могут быть функциями от `VIEW` (например `dialog: {state:'list', selId: VIEW.cpId}`),
  а `render()` — синхронным: клик по элементу меняет `VIEW` и перерисовывает `#frame`.

## 3. Живые переходы вместо «статичных картинок»

Разметка несёт `data-go="<id состояния>"`, один делегированный обработчик клика на `#frame`
переключает состояние. Кликабельно то, что в реальном интерфейсе запускает сценарий:
«Оплатить» на экране заказа → форма оплаты; клик по безналичному типу → окно выбора контрагента;
строка списка → «контрагент выбран»; «Выбрать контрагента» → «оплата применена»;
«Отмена» в окне → «тип оплаты сброшен» (это требование спеки, а не украшение).

**Живой поиск фильтрует строки на месте, а не перерисовкой** — иначе теряется фокус и курсор:
`input` → у каждой строки проверяем `data-name`, ставим `r.hidden`, при пустом результате добавляем
заглушку «Ничего не найдено». Заглушку при следующем вводе снимать (`list.querySelector('.cc-cp__state')` → remove).

## 4. Правки поверх ДС, которые почти всегда понадобятся

Для экранов со списком/селектом/поиском (модальное окно, форма) нужен один и тот же набор, каждый —
с комментарием `/* косяк ДС: … */` и записью в `DS/fixes.md`:

| Что | Число в ДС | Что делаем в каркасе |
|---|---|---|
| `.ds-select-container` | `width:240px`, `min-height:406px` | `width:<нужное>; min-height:0` — окно по контенту |
| `.ds-select-item` | `width:258px` | `width:100%` + правому слоту `margin-left:auto` (значение справа) |
| `.ds-search` | `width:243px` | `width:100%`; `<input>` внутри — класс каркаса (у ДС класса для поля нет) |
| `.ds-select-form` | `width:250px` | `width:100%` — **селектор писать `.cc-field.ds-select-form`** (элемент САМ `.cc-field`, а не потомок: `.cc-field .ds-select-form` не матчится и ширина молча остаётся 250) |
| служебные слоты `__element-left/__element-right`, `ds-element-select` | `background:#ffffff` | `background:transparent` — иначе перекрывают ховер и выбранное |
| выбранная строка | состояния Selected в CSS нет (в Фигме есть) | `.is-selected` — фон Neutral/50 + акцент текста/иконки |
| текстовые элементы автогена (`__text`, `__label-up/down`, `ds-status__content`, `ds-table-*__label`) | `background` = цвет текста | `background:transparent` |
| `.ds-list-container__divider` | фон `#ffffff` — линии не видно | между строками ставить компонент `<hr class="ds-divider">` |
| `.ds-table-header-row/-content-row` | `flex-direction: column` | `.ds-table .ds-table-header-row, .ds-table .ds-table-content-row{flex-direction:row;width:100%}` |
| `Radio button` / `Checkbox` | в `components/index.css` НЕ подключены ни контрол, ни иконки | догрузить `<link>` на `Radio-Button_DS/radio.css` + `radio-icons.css` (иконки — svg-фон, лигатуру в `__box` не ставить) |

Замеры «до/после» этих правок — в `DS/fixes.md`, пп. 34–40 (15.09.2026): зазор иконка→подпись
радиокнопки 0 → 8 px при боксе 20×20; поле контрагента 250 → 378 px; выбранная колонка типа оплаты 181 px.

Состояния загрузки/пустоты: в ДС их нет. Проверенный приём — иконка `autorenew` + `@keyframes` вращение
(прецедент — спиннер в кнопке на страницах рекомендаций) и центрированный текст-подпись; текстовая
подсказка вне поля собирается элементом `ds-input__support` (12 px, #616161).

## 5. Проверка перед показом (без неё не отдавать)

1. `node --check` по инлайновому скрипту: вытащить `<script>` регуляркой в `%LOCALAPPDATA%/Temp/*.js`.
2. Скриншот на КАЖДОЕ состояние в `%TEMP%/cc-shots/`:
   `chrome --headless=new --hide-scrollbars --no-proxy-server --user-data-dir=<свежий на состояние>
   --window-size=1300,1500 --virtual-time-budget=4000 --screenshot=… "<url>?state=<id>&ui=0"`
   и **посмотреть глазами** (`vision_analyze`) — в этой сессии так нашлись: слипшиеся radio,
   пустое поле поиска вместо запроса в состоянии «поиск», сцена, где сценарий показывал не то, что
   обещал текст заметки.
3. Числа — `scripts/probe-page.py` (iframe + `<pre id="out">`): ширина колонок, зазоры, переполнение
   (`scrollHeight > clientHeight`), `disabled`/фон кнопок, ширина полей, число строк списка.
4. Клики — той же пробой через синтетические события:
   `el.dispatchEvent(new w.MouseEvent('click', {bubbles:true}))` по цепочке сценария, печатать состояние
   после каждого шага (элемент → выбор строки → кнопка окна → «Применение»). Так проверяются
   «живые» переходы без ручного тыканья.
5. ⚠ `--dump-dom | grep -c 'class="ds-'` считает и CSS из `<style>` на самой странице — числа
   завышены; считать по разметке (или вырезать `<style>`), не докладывать эти цифры как «сколько
   компонентов на экране».

## 6. Куда писать результат и что доложить

- Страница — `Prototypes/<модуль>-<фича>.html`; ссылку на неё — строкой в `readme.md`
  (раздел модуля), пробелы ДС — новыми пунктами в `DS/fixes.md`, **полным текстом** `%LOCALAPPDATA%`-путей
  не обещать.
- В `Prototypes` и `components-web` — **не коммитить** (это их собственные репозитории с remote).
- Отчёт владельцу: адрес страницы одной строкой (самому не открывать), таблица состояний
  «что показано → что измерил», список пробелов ДС, затем **допущения**: нет ссылки на спеку → сделано
  по тексту; данные экрана правдоподобные, не из макета; спорные решения по композиции (форма оплаты
  панелью справа или модальным окном; колонка = тип оплаты или группа типов) — назвать и спросить.
  Finaльные макеты в Figma не делать молча: это отдельный шаг, ждать решения владельца.
- Если по ходу работы «локальный сервер не отвечает» (`curl` → `Empty reply from server`),
  это висящий старый процесс: `netstat -ano | grep ':8899'` → `cmd /c "taskkill /F /PID <pid>"` →
  `python serve.py 8899` в фоне; владельца предупредить, что его запущенный сервер тоже надо перезапустить.
