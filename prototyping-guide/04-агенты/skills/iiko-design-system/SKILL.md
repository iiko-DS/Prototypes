# iiko Design System — работа с репозиториями ДС

## When to Use

- Правишь или собираешь компонент/прототип в `components-web` / `Prototypes`.
- Переводишь компонент на мобилу, работаешь с режимами Desktop/Mobile или темами.
- Ответ владельцу — по-русски и по факту, без жаргона.

Подробности по классам задач (читать перед работой): проверка правок замером —
`references/prototype-change-verification.md` + `scripts/probe_page.py` (проба и снимок — из актуального файла).

- `scripts/probe-headless.py` — прогон страницы в headless Chrome с впрыснутой JS-пробой и печать
  результата (замеры и клики без открытия браузера).

### Git — корень `DS` под версиями (2026-09-13, по просьбе владельца)

«Делай гит чтобы ничего не удалялось.» Репозиторий `DS` (`github.com/iiko-DS/DS`, ветка `main`,
`core.autocrlf=false` — иначе CRLF-файлы данных меняются при checkout) — это
вся рабочая папка: под версиями и обе
папки слоёв ДС — `components-web/` и `components-mobile/`, плюс `.github`, `.gitignore`.
Репозиторий `Prototypes` — отдельный, лежит **рядом** с папкой `DS` (`github.com/iiko-DS/Prototypes`).

- Коммитить после каждой принятой правки: тогда `git checkout -- <путь>` возвращает файл,
  `git diff` показывает, что уехало, `git log --oneline` — след. До этого репозитория
  потерянные превью восстанавливать было нечем.
- Windows/MSYS: нативный git не понимает MSYS-пути — `git -C /c/Users/…` отвечает
  `fatal: cannot change to …`. Передавать `C:/Users/…` (прямые слэши) или сначала `cd`.

#### Публикация на GitHub: часть файлов уезжает, часть нет

У файла нет флага «опубликован» — публикуется **коммит**: что отметили (`git add` или галочкой) и
отправили (`git push`). Так это и объяснять владельцу (его вопрос: «я думал есть такая функция
опубликовать или нет — я ошибся?»): галочки есть, но в момент коммита (VS Code «Staged Changes»,
GitHub Desktop), а «не публиковать никогда» — `.gitignore`. Состояние рабочего места: `DS` —
приватный репозиторий (`github.com/iiko-DS/DS`), внутри — обе папки слоёв ДС; `Prototypes` —
отдельный приватный репозиторий рядом (`github.com/iiko-DS/Prototypes`). Публичного сайта пока
нет: Pages у приватных репозиториев не включается; когда включат — ДС будет отдаваться по
`https://iiko-ds.github.io/DS/…`. Контроль отправки — `git diff --cached --name-only` (единственный
источник правды), до правки — сухой прогон `git add --dry-run -A` (на прототипах это 98 файлов),
отмена — `git restore --staged`, `git reset --soft HEAD~1`, `git rm --cached`. Прототип «как есть» на
GitHub откроется текстом (ссылки `../components-web/*` и `app-header/`, `app-sidenav/` в репозиторий
`Prototypes` не входят), а публичного сайта ДС пока нет — Pages не включён. Порядок команд, репетиция
на живом репозитории и проверка видимости без токена —
`references/git-publishing-and-selective-commits.md`.

Файлы `components-web`:

- `tokens.css` — **генерируется** из Figma (1743 переменные, 10 коллекций; в
  шапке дата выгрузки). Руками не править.
- `styles.css` — выгрузка плагина v2 («Не править руками»): текстовые/эффект-стили,

  `await document.fonts.load(...)`, а не мгновенным `document.fonts.check()` — он даёт `false` до загрузки.
- `iiko-ds-spec.md` — ~700 КБ, единый источник для людей и ИИ. **Читать только
  точечно** (`search_files`/grep по якорям: «#### Button `», «Карта классов»,

- `components/index.css` — @import-агрегатор всех компонентов;

## Правила, которые связывают любую правку

Из `iiko-ds-spec.md` (раздел «Общие правила»), кратко:

0. **Не гадать.** Каждое значение — из источника: токен, Figma-параметр в
   спеке, или файл сравнения в прототипах. Нет значения в источнике → СТОП и
   вопрос, а не «подберу похожее».
1. **Никаких хардкодов** — цвета, радиусы, отступы, размеры, шрифты только
   через `var(--ds-*)`.
2. **Компоненты только из ДС.** Свои классы — лишь для каркаса страницы
   (page/grid/dialog-frame), у которого нет ДС-компонента.
3. Классы `ds-*`, модификаторы через `--` (`.ds-btn--m`), элементы `__`
   (`.ds-btn__label`). Одинаковых элементов ≥2 → групповой компонент.
4. **Иконки — Google Material Icons лигатурой** `<span class="material-icons" style="font-size:20px">имя</span>`
   (спека переписана владельцем 11.09.2026: «вставляются по имени, обязательного списка нет»). Свои SVG —
   только бренд-иконка iiko; «похожих» самодельных иконок и PNG не рисовать. Размер — через `font-size`
   (слоты ДС `__icon` центрируют содержимое), цвет наследуется. Строка «SVG 20×20 (не шрифт)» устарела.
5. Размеры компонентов берутся из компонентных токенов
   `--ds-<компонент>-<размер>-size-<свойство>` (коллекция `Component` в
   `tokens.css`), а не из общих `--ds-space-*` по месту.

## Две независимые оси

| Ось | Что меняет | Где живёт |
|---|---|---|
| **Тема** | только цвет | `themes.css`, `data-theme` |
| **Режим/платформа** | только размер: высоты, паддинги, кегль, тач-зоны | `modes.css`, `data-mode` |

Разметка и классы **одни и те же** для десктопа и мобилы. Модификаторы
`--mobile` и отдельные «мобильные подмножества» не создавать.

### Механика режима

- Дефолт (атрибута нет) = Desktop: значения из `tokens.css`.
- `[data-mode="mobile"]` переопределяет **только отличающиеся** токены;
  совпадающие не трогать — они остаются алласами на примитивы.
- Атрибут можно ставить на `<html>` (весь экран) **или на любой контейнер** —
  тогда десктоп и мобилу видно рядом на одной странице. В Figma так нельзя
  (режим глобальный на файл), в коде — можно; это лучший аргумент для показа
  разницы дизайнерам.
- Порядок подключения: `font.css → tokens.css → modes.css → themes.css →
  components/index.css`. Специфичность `[data-mode="mobile"]` и `:root`
  одинаковая, поэтому решает порядок: `modes.css` обязан идти после `tokens.css`.
- `modes.css` — ось размера, а не место для компонентной логики: сюда попадают
  только переопределения токенов (+, при необходимости, общие мобильные
  правила уровня платформы). Компонентный CSS остаётся в `components/`.
- Режимы живут отдельным файлом, потому что `tokens.css` генерируется. Когда
  экспортёр плагина начнёт писать `[data-mode]` сам — блоки переезжают в
  `tokens.css`, `modes.css` уходит. Так и говорить пользователю: это мост.

## Как переводить компонент на мобилу (классификация)

Из `desktop-to-mobile-plan.md` и `mobile-mode-notes.md`:

| Категория | Признак | Решение |
|---|---|---|
| 1. Только значения | тот же набор свойств/цвет/радиус/состояния, отличаются числа | режим `data-mode="mobile"` (общие токены) |
| 2. Структура | меняется состав/порядок элементов | отдельный `-mob`-компонент |
| 3. Скрыт/заменён | элемент уходит или заменяется | правило лейаута, не компонент |

Ориентир тач-эргономики: Material — 48 dp, минимум для веба — 44 px (iOS).
Если карточка/экран перестраивается — это категория 2/3 и режим не поможет.

Для категории 2 вариант — это **файл в мобильном слое**:
`components-mobile/components/<Имя>_DS/<вариант>.css` + `@import` в `components-mobile/components/index.css`
(первый такой — `Stepper_DS/stepper-vertical.css`, 11.09.2026). Два капкана, проверенные на нём:
мобильный слой подключается **до** `components-web/components/index.css`, поэтому селектор варианта
пишется с большей специфичностью (`.ds-stepper.ds-stepper--vertical`, иначе базовый `align-items`
остаётся и раскладка разваливается), и **любая** страница с панелями `data-mode="mobile"` обязана подключать
`../../components/index.css` (`../components/index.css` внутри `components-mobile/prototypes/`) — без этой
строки мобильные файлы на страницу просто не попадают. Так `prototypes/button-modes.html` жила без них:
демо «На всю ширину (Bottom action bar)» показывало кнопку 100,6 px при строке 552, группа — 79,2 + 100,6.
Если демо на мобильной панели противоречит правилу мобильного слоя, сначала проверять эту строку.
Рецепт, замеры и кейс Stepper: skill `iiko-ds-components`, `references/mobile-structural-components.md`.

Второй мобильный файл — про **поведение**, а не структуру: `Button_DS/button-group-mob.css`.
На мобиле кнопки заполняют строку: одна — 100 % (`.ds-btn--full-width`), две и больше в
горизонтальной группе — делят строку поровну. Он же закрывает старое «не всё подтянулось из
дизайн системы»: поведение становится правилом ДС, а каркас страницы ссылается на класс, а не
повторяет его эффект (обёртку `.btnfull` убрали). На странице это ещё и строка таблицы
«Что меняется на мобиле» — «Ширина в строке»: Desktop «по содержимому (HUG) — в ряду кнопки своей
ширины», Mobile «заполняет строку (fill): одна кнопка — 100 %, две и больше — делят поровну».
Рецепт, замеры (327 → 159,5 + 159,5;
десктоп без изменений) и капканы — skill `iiko-ds-components`, `references/mobile-button-row-fill.md`.

### Приём: высоту элемента не токенизировать

Figma-элементы с HUG-высотой не дают токена высоты, а в примитивах может не
быть нужного числа (например Base Size кончается на 40 px, а мобильной кнопке
нужно 44). Не выдумывать примитив и не хардкодить — собирать высоту из того,
что есть:

```css
height: calc(var(--ds-button-m-size-pad-top) + var(--ds-button-m-size-pad-bottom)
              + var(--ds-typography-body-line-height-s));   /* 8+8+20 = 36 */
```

Тогда режим переопределяет только паддинги и кегль, а мобильные 44 px
(`12+12+20`) приходят сами. Тот же приём даёт 28 и 24 для S/XS.

**На мобиле такая высота задаётся `min-height`, а не `height`.** Однострочная подпись даёт ровно 44
(`12 + 20 + 12`), но если подпись переносится на вторую строку (паттерн «Длинная подпись»), фиксированная
высота её режет: содержимому нужно 45 px при 42 доступных внутри рамки 44. Владелец: «когда я меняю высоту
кнопка кажется не правильно реагирует и не учитывает 2 строчку текста». Чинить в двух местах, и обе нужны:

1. мобильный слой `components-mobile/components/Button_DS/button-touch.css` —
   `[data-mode="mobile"] .ds-btn--m/--s/--xs{min-height:44px}` вместо `height:44px`; иконки
   `.ds-btn-icon--*` остаются фиксированными 40 × 40 (их содержимое не переносится);
2. значения в данных: правка «Высота» отдаёт `min-height:@px` вместо `height:@px` — иначе живое правило
   правого экрана снова прижимает кнопку (9 файлов данных).

Замеры после правки: «Длинная подпись» без правки — 66 px; «Высота 44» → 66 (было 44 с обрезкой);
52 → 74; 64 → 86 — кнопка растёт вместе с паддингом по формуле синхронизации, вторая строка всегда внутри;
короткая подпись при «Высота 44» — ровно 44. Проверка — прогон по всем паттернам с рекомендованной высотой
и критерий «выход содержимого за рамку» (`scrollHeight > clientHeight`).

Для квадратных компонентов (Button icon) приём работает по обеим осям:
`width: calc(pad-left + pad-right + icon-size)` и
`height: calc(pad-top + pad-bottom + icon-size)` — M 8+8+20 = 36, S 4+4+20 = 28,
XS 4+4+16 = 24. А там, где у контейнера высоты нет **вовсе** (Button toggle) — её и не
добавлять: по умолчанию он HUG, и высоту ему даёт содержимое. У переключателя содержимое —
**инстансы Button** (он надслойка над ними, см. следующий раздел), поэтому его высота = отступы трека
+ высота кнопки внутри, и на мобиле она растёт вместе с Button; своей размерной шкалы у переключателя
в токенах нет — и выдумывать её не надо, а сказать об этом.

### Надслойки над другими компонентами

Некоторые компоненты ДС — не самостоятельные контролы, а **контейнеры над инстансами других**: Button
toggle = трек над `.ds-btn` (в Figma слот «Button container»). Признак в токенах: у такого компонента есть
только отступы/радиус/фон, а размеров сегментов нет. Тогда:

- в CSS компонента — только геометрия и фон трека, вид сегмента целиком задаёт вложенный компонент;
- мобильных значений ему не нужно: сегменты растут по режиму своего компонента, трек — за ними;
- `__label`/`__icon` в его CSS — обычно артефакт автогена (содержимое — элементы вложенного компонента),
  в разметке не используются, но и не удаляются без спроса;
- не путать надслойку с контролом: если принять трек за сегмент, получится «выбранный» белым на белом и
  желание подставить токены соседнего компонента — этого делать нельзя.

## «Создай прототип по описанию задачи» — доработка фичи в Prototypes

Отдельный класс: приходит текстовое описание доработки (новая колонка в форме, модальное окно,
состояния загрузки/пустоты, карточка со платежом) и «примени нашу дизайн систему и инструкцию по
созданию прототипов». Ссылка на спеку часто НЕ доезжает — делать по тексту и перечислять допущения
(«не отвечать на неоднозначную задачу только вопросами»).

Формат — **один файл на всю доработку с переключателем состояний** (принят владельцем):
шапка ревью `.modes-bar` (название, «Подсказки ДС», `<select>` состояний, ← →, счётчик) + плашка
заметки «Что на экране / Почему так» + кадр `.panel > .frame` с шапкой и рельсой приложения;
состояние в адресе (`?state=<id>`, `?ui=0` — чистый кадр), переходы живые (`data-go` + делегированный
клик), поиск фильтрует строки на месте, а не перерисовкой. Разметка — только компоненты ДС;
обязательный комментарий в `<head>` с «ОТКУДА ЧТО ВЗЯТО» и честной строкой про отсутствующий макет.

Проверять перед показом: `node --check` инлайнового скрипта, скриншот на КАЖДОЕ состояние и просмотр
своим зрением, числа — `scripts/probe_page.py` (ширины, зазоры, переполнение), клики —
синтетическими MouseEvent по цепочке сценария. Не коммитить в `Prototypes`/`components-web`
(их собственные репозитории); ссылку добавлять в `readme.md`, пробелы ДС — в `DS/fixes.md`.

Таблица правок поверх ДС (жёсткие ширины 240/258/250/243, белые служебные слоты, отсутствующие
состояния Selected/загрузки/подсказки), рецепт состояния, форма отчёта и капканы —
`references/feature-prototype-page.md`.

## Формат демо-страниц для пользователя

Страница компонента — для дизайнеров/продукта, не для разработки. Пользователь прямо
просил убрать «всю техническую инфу»: на странице только то, что нужно, чтобы понять
изменение и передать дальше продакту.

| Оставляем | Убираем со страницы |
|---|---|
| Две панели рядом: Desktop (`data-mode="desktop"`) и Mobile (`data-mode="mobile"`), один и тот же markup | Таблицы токенов, расчёты высот, ссылки на CSS |
| «Что меняется» — короткая таблица Что / Desktop / Mobile | Замеры `getBoundingClientRect`, таблица измерений |
| «Почему так» — 1–2 фразы простыми словами (палец вместо курсора, минимум тач-зоны) | Блоки «что рекомендуют платформы» с числами и списком первоисточников |
| «Итог» — что остаётся, что убираем, что решает владелец | Внутренние пути, имена токенов |

Категория изменения — тремя словами: «только размеры», «размеры + поведение», «структура».
Техническую часть (токены, спека платформ, ссылки, замеры) собирать и хранить отдельно,
на страницу не выводить. Позже — отдельный раздел
«как это выглядит в интерфейсе и как происходит переход» (для продукта и разработчика).


### Как отдавать ссылку на страницу (проверено 11.09.2026)

**Самому не открывать** — пользователь попросил: «Не нужно мне постоянно открывать автоматом страницы
с компонентами». Давать полный адрес текстом одной строкой; `cmd /c start` — только по прямой просьбе.

В ACP-панели VS Code ссылки на локальные файлы **не работают**: `file:///…` и markdown-ссылка
на него выглядят как ссылка, но клик ничего не делает («Ссылки не рабочие»). Рабочий приём —
поднять локальный сервер и отдать http-адрес текстом:

```bash
# из корня DS, в фоне (живёт до конца сессии)
python -m http.server 8899 --bind 127.0.0.1 --directory C:/Users/asukharev/GitHub/iiko-DS/DS
# открыть в браузере по умолчанию
cmd.exe /c start "" "http://127.0.0.1:8899/<путь-страницы>/button.html"
```

Пути писать **полные**, от корня `C:/Users/asukharev/GitHub/iiko-DS/DS` — он просил об этом прямо
(«пиши тут полные ссылки всегда»). Его «дай ссылку» значит «дай адрес, который откроется»; открывать
за него не надо — назвать адрес одной строкой и ждать.

Проверено 11.09.2026 на исходнике расширения (`formulahendry.acp-client-0.2.0/dist/extension.js`):
markdown рендерится через `marked`, но обработки открытия ссылок в расширении нет
(`openExternal`/`vscode.open` не вызываются). Поэтому клик **не открывает ничего вообще** —
ни `file://`, ни `http://127.0.0.1:8899`; не перебирать форматы ссылок второй раз. Работает:
открыть самому (`cmd.exe /c start`), отдать адрес текстом для вставки в браузер, ярлык `.url`
на Рабочем столе (`[InternetShortcut]` + `URL=file:///C:/…`) либо папка в Проводнике
(`explorer.exe /select,"<файл>"`) — двойной клик по файлу откроет браузер.

Git-публикацию (commit/push в `components-web`, Pages) не предлагать как способ решить проблему
со ссылкой: на это он ответил «Не надо уводить пока на гит».

## Отчёты владельцу файлом (PDF) и разбор чужих репозиториев

Отдельный класс задачи: «проанализируй чужой репозиторий/скилл и сопоставь с нашей ДС» + «оформи
файлом». Рецепт, капканы и форма ответа — `references/reports-as-files-and-external-repo-reviews.md`;
коротко о правилах:

- Готовый PDF — **на Рабочий стол** (`C:\Users\asukharev\Desktop\<имя>.pdf`), HTML-заготовка и PNG для
  проверки — в `%LOCALAPPDATA%\Temp\ds-report\`. В папки ДС (`components-web`, `components-mobile`,
  `Prototypes`) ничего лишнего не писать. Путь отдавать полным текстом, файл самому не открывать.
- Сборка PDF: HTML → headless Chrome (`--headless=new --user-data-dir=<свежий> --no-pdf-header-footer
  --print-to-pdf=C:/…/x.pdf`); в CSS первым шрифтом `Segoe UI` (кириллица без настройки) и
  `print-color-adjust: exact` (иначе плашки не печатаются). Проверить `pdf_read.py --meta` (page_count)
  и просмотреть страницы своим зрением — **не отдавать PDF, не посмотрев его**.
- Разбор чужого репозитория начинать с дерева `api.github.com/.../git/trees/<branch>?recursive=1`
  (400+ файлов одним запросом) и докладывать цифрами, а не впечатлениями: что там инструкции для
  агента / тесты / инфра пакета, а что продукт. Вывод «нужно ли нам так же» — по функции, таблицей
  «их папка → наш аналог → нужно ли»; в конце «что взять» (1–3 мелких пункта) и «чего не делать».
- **Файл обычно уже открыт у него в просмотрщике — перезапись молча не выйдет.** Chrome отвечает
  `Failed to write file … файл занят другим процессом (0x20)`, `cp -f` — `Device or resource busy`.
  Не биться и не удалять: собрать в `%LOCALAPPDATA%\Temp\ds-report\` и отдать **тем же документом с
  суффиксом** (`<имя>-v2.pdf`) одной строкой: файл открыт, перезапишу после закрытия. Проверено 15.09.2026 на
  `iiko-ds-structure.pdf` — второй сборке пришлось идти как `iiko-ds-structure-v2.pdf`.
- **`break-inside: avoid` на таблицах рвёт страницу наполовину.** Готовая таблица целиком переезжает на
  следующую страницу, а на предыдущей остаётся полстраницы пустоты (первая сборка так и вышла на 6 страниц
  вместо 5). Держать `avoid` на `tr` и плашках (`.lead/.note/.stop/.chain`), таблицам давать переноситься;
  после правки CSS страницы **пересобирать PDF и просматривать заново** — нумерация и обрывы сдвигаются.

### Аудит файлов дерева («все ли файлы нам нужны»)

Следом за разбором структуры владелец спрашивает: «А все ли файлы нам нужны или от чего то можно
отказаться или наоборот добавить?» Это инвентаризация **своего** дерева: три замера (ссылочный
анализ, дубли по MD5, вес в git), отчёт блоками A/B/C с опровержимым доказательством на каждую
строку — и **без единого удаления**. Находки 15.09.2026, метод и форма ответа —
в истории задачи; прогон замеров — `python scripts/audit-repo-files.py`
(ничего не меняет).

- **«Нигде не упомянут» ≠ «не нужен».** Часть файлов читается скриптами через `glob` по каталогу
  (например, PNG-выгрузки), поэтому перед вердиктом искать потребителя двумя способами:
  по имени файла и по каталогу/расширению (`open(`, `glob`, `import`). Нулевой grep — ещё не приговор.
- **Вес считать через `git ls-files` + `os.path.getsize`**, а не `git cat-file -s` на каждый файл:
  на 1167 файлах терминал уходит в таймаут и не отдаёт ничего (проверено 15.09.2026).
- В отчёт — вес, доказательство и **риск отказа** на каждую строку, отдельная плашка «не отказ,
  а наоборот» для того, что правильнее починить, и внизу «Ничего не удалялось и не менялось — это отчёт».
  Снятие файлов с версионирования и правки в `components-web` — отдельные решения владельца.

## Pitfalls

- **Не начинать с HTML.** Сначала источник значений, потом токены, потом код.
- **Не токенизировать в деньги/дизайн правки без источника:** значения бывают
  только из токенов, спеки или файлов сравнения в прототипах.
- **Генерируемые файлы не править** (`tokens.css`, `styles.css`); соглашение
  попадает в `iiko-ds-spec.md` и в `modes.css`.
- **В сгенерированном компонентном CSS ловить два дефекта:** (а) комментарий,
  «съевший» селектор (`.ds-btn--xs /* … */ .ds-btn__label {` — компилируется как
  потомок); (б) дубль общего блока ниже по файлу, который перебивает размерные
  варианты (общий `.ds-btn__icon { font-size: 20px }` отменял 16 px у XS).
  Размерные варианты определять **после** общего блока.
- **Размер иконки задаётся `font-size` у лигатуры, а не у svg.** Слоты ДС (`__icon`, `ds-arrow`,
  `ds-arrow-select`) — `inline-flex` с размером из токена (`--ds-size-4x` / `-5x` / `-6x` = 16 / 20 / 24),
  лигатура ставится внутрь с `font-size` того же размера. В каркасе страниц нужен `line-height: 1`
  (`.panel .material-icons{line-height:1;display:inline-block}`), иначе глиф съезжает.
  Прежнее правило «SVG не масштабируется `font-size`» относилось к самодельным SVG — их больше нет.
- **Спросить перед правкой файлов**, если инструмент правки отклоняется клиентом
  (ACP): см. `hermes-desktop-backend-diagnostics`, раздел про approval-гейт.
- **Литеральный `%` в шаблоне страницы ломает сборку.** `page()` в `build.py` использует
  %-форматирование: знак процента внутри вставляемой разметки, CSS или JS даёт
  `TypeError: not enough arguments for format string` и роняет сборку всех страниц. Писать словами
  («60 процентов») или экранировать (`%%`). При правке `screens_card()` следить, чтобы число `%s`
  совпадало с числом аргументов: строка меню берёт ОДИН `%s` со склеенным
  `review_tools() + строка прогресса + пункты` — я поставил три подряд и получил тот же `TypeError`.
- **`\n` внутри JS в %-шаблоне превращается в реальный перевод строки и убивает скрипт страницы.**
  `\n`, записанный в исходнике `build.py` одним слэшем, при сборке разворачивается в настоящий перевод
  строки: регулярка `.replace(/\n/g, ' ')` рвётся, и **весь `<script>` страницы не выполняется молча** —
  меню паттернов не переключает, плашка текста и строка прогресса пустые, ошибок в консоли нет, потому что
  синтаксис падает целиком. Симптом легко принять за «мой код не подключается». В исходнике писать `\\n`.
  Диагностика, которая находит это за один прогон: вытащить все каждый
  `<script>` из собранных страниц и прогнать `node --check`; проверено 14.09.2026 — показал строку с разорванной
  регуляркой).
- **Новый блок страницы получает правила каркаса только явно.** Примеры внутри карточки живут вне
  `.panel` и `.phone`, поэтому до них не доходят ни нейтрализация артефактов автогена
  (`background` задан тем же токеном, что `color` → текст рисуется чёрной/серой плашкой), ни снятие
  замороженных высот контейнеров, ни ограничение фиксированных ширин ДС (диалог 500 px, однострочный
  снекбар 370 px). Решение — в `build.py` генерировать копии правил каркаса для контейнера блока
  (`.pat__panel`), а не перечислять классы руками; одного `.panel`-списка мало.
- **Контент — по реальным кейсам и признанным специалистам, а не только по докам платформ.**
  Требование владельца: «Нужны реальные кейсы и применение от больших компаний или известных
  специалистов UX/UI гуру». К каждой теме — кейс продукта (Gmail, iOS Mail, WhatsApp, B&H Photo,
  Overcast, YouTube, Walmart) и разбор авторитета (Nielsen Norman Group, Baymard, Smashing), каждый
  с дословной цитатой и адресом, сверенной вытаскиванием страницы, а не по памяти. Что подтвердить
  не удалось — так и писать. Собранные и проверенные цитаты: `references/verified-mobile-ux-sources.md`.
- **Обёртка вокруг кнопок ломает селекторы прямого потомка.** Стиль панели отчёта стоял как
  `.review__tools > button`; стоило обернуть кнопки в строку `.review__row` (поле «Кто смотрит» +
  подсказка имён), как они потеряли рамку, фон, паддинги и радиус — остался голый текст, и владелец
  сказал «что-то с кнопками случилось». Правило: добавил контейнер в генерируемую разметку — grep по
  `> <тег>` в CSS каркаса и дописать селектор (`.review__tools > button, .review__row > button`), затем
  проверить `getComputedStyle` (padding/рамка/фон) — глазами такая потеря стиля не видна.
- **Проба обязана выбирать конкретный элемент, а не объединение селекторов.** Ошибка цены ложного вывода:
  в замере «Длинной подписи» я взял кнопку как `.ds-btn, .ds-btn-icon`, а подпись как `.ds-btn__label`
  отдельно — первым матчем оказалась иконка шапки (40 × 40), а подпись была от кнопки в теле, и «подпись
  вылезает за кнопку на 283 px» стало выводом из двух разных элементов. Мерить адресно
  (`.btnbox .ds-btn` + `.btnbox .ds-btn__label`), вердикт про обрезку давать по одному элементу
  (`el.scrollHeight > el.clientHeight`). Так «баг» не выдумывается там, где его нет.
- **Одно имя класса на две разные вещи ломает раскладку.** `.review__row` был и рядом статусов в плашке
  паттерна, и (после моей правки) строкой кнопок в оболочке: правило оболочки `flex:0 0 100%` победило по
  порядку в файле, ряд статусов растянулся на всю ширину и выдавил заголовок — владелец: «Сломался заголовок
  и кнопки у описания паттерна». Заголовок стал 76 × 120 px в столбик вместо 310 × 24 в одну строку. Лечится
  разными именами (стало `.review__buttons`); перед новым классом — grep по CSS на это имя, после правки —
  сверять числами: заголовок одной строкой, правый край ряда кнопок = правый край плашки (1842 = 1842).
- **`\n` внутри JS-строки %-шаблона — тот же мёртвый скрипт.** Собранное подтверждение сброса с `\n\n`
  в исходнике развернулось в реальный перевод строки внутри `confirm('…')`, и страница потеряла весь скрипт.
  Многострочный текст в `confirm`/строках JS просто не писать — собирать одной строкой через `+`.
- **Обёртке карточки нужен закрывающий `</div>` в том же патче.** Разметку «Почему так»/«Итог»/«Общее…»
  я оборачивал в `.card__head` + `.card__body` двумя заходами, и в промежутке карточка осталась
  незакрытой. После таких правок сверять в собранном файле баланс тегов (`<div` против `</div>` — числа
  должны совпасть) и вхождения `data-fold`.
- **Новой странице (в том числе оболочке) — шрифт иконок в шапке.** `index.html` не подключал
  `family=Material+Icons`, и владелец увидел кнопки как «Отчёт xls / JSON / expand_more / restart_alt /
  Сброс»: «Что-то с кнопками не так». Лигатура без шрифта рисуется своим именем.
- **Правка `serve.py` не действует без перезапуска сервера.** Сервер живёт между сессиями: старый
  процесс отвечает на POST `501 Unsupported method ('POST')`, а иногда и вовсе висит — `curl` по
  `http://127.0.0.1:8899/…` отвечает `Empty reply from server` (порт в `netstat` LISTENING, страница
  в headless снимается пустой/одинаковой). Порядок: `netstat -ano | grep ':8899' | grep LISTENING` →
  убить процесс → `python serve.py 8899` в фоне из корня `DS`.
  ⛔ В MSYS `taskkill //F //PID <pid>` (двойной слэш) НЕ работает: MSYS подставляет путь и отвечает
  «неправильный параметр - '//F'». Вызывать через cmd: `cmd /c "taskkill /F /PID <pid>"`.
  Владельца предупредить, что свой запущенный сервер тоже надо перезапустить.
- **Странице в `Prototypes` сервер не нужен, а вот пробе — флаг.** Прототипы открываются по
  `file://` (CSS/шрифты тянутся из сети), поэтому headless-прогон идёт без `serve.py`: скриншот —
  `--headless=new --window-size=1400,5300 --virtual-time-budget=6000 --user-data-dir=<свежий>`; числа
  и клики — пробой в `%TEMP%` с `<iframe src="file:///…">` **плюс `--allow-file-access-from-files`**,
  иначе `contentDocument` чужого файла недоступен. Проба управляет состоянием через
  `iframe.contentWindow.store.stage=…; paintAll()` и печатает JSON в `<pre id="out">`.
  Так проверяется и «список не дёргается» (высоты строк в каждом состоянии), и клики
  (бамп, повторный клик, роли) — и никого не надо просить что-то разрешать в браузере.
  **Числа и кадр — двумя обёртками:** проба держит iframe вне кадра (`left:-99999px`, чтобы не мешал),
  поэтому `--screenshot` по самой пробе даёт **пустой файл** — кадр снимать отдельной обёрткой с видимым
  iframe нужной высоты, а регион для кропа в `vision_analyze` считать позиционной пробой (y `h2` и блоков
  на полной высоте страницы): на кадре 1400 × 3300 нужный блок иначе не найти.
  **Откат называть только по своему репозиторию:** страницы прототипов лежат в `Prototypes` (своя git-история),
  поэтому из корня `DS` `git log -- <путь>` и `git status` по ним пусты — сначала `git ls-files` / `git -C`,
  иначе обещанный `git checkout` не сработает.
- **Токены, объявленные на корпусе экрана, не доходят до блоков вне него.** Если палитра объявлена
    на корпусе, а блок добавлен вне его, `var(…)` не находится, и элемент молча рисуется серым —
    браузер об этом молчит, видно только на скриншоте. Палитру объявлять в `:root`, корпус оставлять
    под геометрию и цвет текста. Тот же класс ошибки, что
  «правила каркаса доходят до нового блока только явно». **Сюда же `box-sizing`:** `.screen,.screen *{box-sizing:border-box}`
  до полосы крупного показа (она вне `.screen`) не доходит, поэтому добавленный пунктир 1 px раздул кнопку
  104 → 106 px, а соседние кнопки-`button` остались 104 — сетку показа повело на 2 px, и глазами это не видно.
  `box-sizing:border-box` держать в самом классе контрола, а после любой правки, добавляющей рамку, размер
  **мерить** `getBoundingClientRect`, а не смотреть.
- **Одна лишняя строка внутри элемента стоит 20 px сдвига.** У строки в карточке
  360 px вторая строка текста поднимает её высоту 62 → 82 px,
  и все строки ниже прыгают вниз. Элемент, у которого меняется счётчик, должен остаться той же высоты:
  счётчик — в существующую строку, подпись — **вместо** прежнего текста, не строкой ниже. Условие
  «список не дёргается» доказывать замером высот во всех состояниях, а не словами.
- **Не пересказывать словами то, что уже видно в интерфейсе.** В строке закрытого блюда я написал
  «✓ Приготовлено» под названием — владелец: «Когда оба подтвердили — приготовлено у блюда писать не
  нужно. Итак понятно что приготовлено по статусу в кнопке и зелёному чекбоксу». Правило: слово-статус
  не дублировать там, где статус читается по заливке кнопки, галочке или канту; оставлять только то,
  что добавляет смысл («Все цеха подтвердили» — про цеха, а не про статус).
- **Украшения на контроле, нарисованные псевдоэлементами, читаются как дефект.** «Разрыв» стрелки
  (тёмная полоса `::after` через центр кнопки и через глиф) владелец снял: «Какая-то хрень. Как будто
  крандашём нарисовали палку вертикальную». Граница проходит так: **нарисованные поверх контрола формы —
  нет, маска по штатной иконке ДС — да**. Ответ на «шаг делится на N нажатий» искали трижды и в итоге вынесли из стрелки: маска-пунктир и иконка
  `line_end_arrow` из набора сняты («Нет, стрелка не подходит»), актуальное направление — квадратная кнопка
  56 × 56 со скруглением 12, внутри **только два элемента** (числа «сколько нажали» белым / «сколько нужно»
  синим и стрелка), прогресс — **тонкая полоса по периметру кнопки**;
  ⛔ заливка от центра до окружности («сектора», `conic-gradient` пирог), круглая кнопка (кольцо) и третья
  полоска внутри кнопки сняты («Сектора, это бред… Кнопка… Никогда не круглая»; «3 визуальных элемента в
  одной кнопке внутри. Это не читается»).
- **Приём, отвергнутый по названию, не угадывать — уточнять форму.** На «сектора — бред» я убрал и круглую
  кнопку, и периметр; владелец имел в виду только заливку от центра («Треугольнички»), а бордер по периметру
  просил вернуть («Верни обратно»). Длинный заход впустую. Одна короткая формулировка в ответе («периметр
  как рамка, внутри только числа и стрелка») и вопрос «так?» дешевле, чем переделка двух итераций.
- **Считать визуальные элементы внутри одного контрола.** Владелец читает 56 × 56 как «одно действие»: три
  слоя (числа + стрелка + полоска/бейдж) внутри одной кнопки — «не читается». Норма — два; третий выносить
  на периметр, в соседний слот или в строку. Альтернативы держать рядом новыми макетами на
  той же странице, а не заменой: ⛔ «Ты не стирай прошлые наброски, делай просто новые».
  **Вариант, предложенный владельцем, собирать сразу и показывать** («Может пунктирую стрелку отобразить?»
  → сделал, принял): объяснять, почему его идея плоха, и только потом делать свою — потерянный ход.
  **Иконку он ждёт из официального набора по имени, а не «похожую»** («Возьми отсюда
  fonts.google.com/icons пунктирную стрелку») — искать имя в metadata набора, проверять замером и
  называть семейство шрифта, в котором она есть: `references/material-icons-vs-symbols.md`.
- **Файлы с кириллицей в пути читать абсолютным путём.** `read_file` по относительному пути
  с кириллицей отвечает `File not found`, при этом
  `ls` в терминале файл видит; полный `C:/Users/asukharev/GitHub/iiko-DS/DS/…` читается нормально. И длинные
  однострочные `grep` с кириллицей и экранированными кавычками не собирать — резать на короткие
  команды, `search_files` или `execute_code` с Python.
- **Radio button и Checkbox не работают «из коробки»: их файлов нет в агрегаторе.** В
  `components/index.css` из `Radio-Button_DS` подключён только `radio-button-label.css`, из `Checkbox_DS` —
  только `checkbox-label.css`. Контрол (`radio.css` — flex, зазор 8, состояния) и иконки
  (`radio-icons.css` — svg-фон вместо лигатуры) надо догружать `<link>`-ом на страницу, иначе
  `.ds-radio` рисуется полусырым: зазор иконка→подпись 0 при боксе 20 px (замер 15.09.2026),
  а лигатура `radio_button_unchecked` в `__box` даёт 24 px вместо 20. В `__box` класть **пустой span**,
  состояние даёт `.ds-radio__input:checked + .ds-radio__box`.
- **Удаление тестового файла видно в `git status` как `D`.** Файлы проб попали в снимок
  `7a528ba` и отслеживаются: свою пробу после прогона либо оставлять, либо удалять вместе с осознанием,
  что это правка дерева (`git checkout -- <файл>` возвращает). Проверять
  `git ls-files <папка>`, прежде чем считать мусор «неотслеживаемым».
- **Видимый отклик там, где нажали.** «При клике на сохранить там где Правка вообще ничего не происходит» —
  запись данных без видимой смены состояния читается как несработавшая кнопка. Отклик ставить в саму точку
  взаимодействия (подпись/подсветка), а не плашкой сбоку.
- **Открытые вопросы не решать молча.** Клик-зона S/XS на мобиле, hover на тач
  (`@media (hover: hover)` меняет и десктопное поведение), 44 vs 48 dp — это
  решения пользователя, их выносить списком.
- **«Поведение на мобиле не меняется» — не подставлять по умолчанию.** Один раз пользователь
  поймал на этом: строка «те же состояния (hover, press, disabled, loading)» оказалась
  неверной, потому что hover на тач не показывается. Прежде чем писать такое, проверить
  `:hover`/`@media (hover: …)` в компонентном CSS. Что говорят платформы и как это
  формулировать — `references/hover-and-states-on-touch.md`.
- **Сначала искать в уже собранных данных, потом идти в интернет.** Рекомендации платформ
  уже разбирались в прошлых задачах — выводы лежат в этих заметках и должны отвечать
  на вопрос за секунды. Консультация по памяти вместо поиска читается как
  «ты зачем опять придумываешь своё»: данных в проекте уже достаточно.
- **Прежде чем просить у владельца доступ — проверить, не настроен ли он уже.** Задача пришла ссылкой
  на `wiki.iiko.ru`, я сразу попросил токен/логин — и получил «Разве у гермеса нет доступа к Jira и
  Wiki iiko?». Порядок: посмотреть `config.yaml` (секция `mcp`, файлы с `mcpServers`), **имена** ключей
  в `%LOCALAPPDATA%\hermes\.env` (значения не печатать), `desktop-plugins/` — доложить фактами, что есть
  и чего именно не хватает, и только потом просить PAT файлом вне репозитория или разрешение в браузере.
  Пробы «страница вообще есть?» (`302 → /login.action?…permissionViolation=true` у HTML, `401` у REST),
  версия Confluence без логина (`ajs-version-number` в `/login.action` → 9.2.2, PAT возможен с 7.9) и
  способы доступа — `references/internal-wiki-and-jira-sources.md`.
- **Не удалять прототипы/демо и не «чистить» ссылки на них по своей инициативе.** Пользователь
  отменил такое решение через час и попросил файл назад. Удалённый/перезаписанный файл
  восстанавливается из истории сессии (`state.db`: полный `content` из `write_file` плюс
  последующие правки, реплей по порядку) — инструмент: skill `session-store-forensics`,
  `scripts/recover-file-from-state-db.py`. Искать сначала там, а не собирать заново по памяти.
- **`web_extract` может ответить `403 Keyless Exa …`** — это не повод останавливаться:
  первоисточники (raw.githubusercontent.com, api.github.com) спокойно берутся `curl -sL`
  в терминале. Обратная сторона: `m3.material.io` и `developer.apple.com` — клиентский
  рендер, curl отдаёт HTML без чисел; числа брать из официальных исходников на GitHub
  (`tokens/_md-comp-*.scss`, `button/internal/_touch-target.scss`, `src/material/**/*.md`)
  или из уже снятых в проекте файлов сравнения.
- **Прежде чем обещать мобильные числа, посмотреть колонку `_mob` в строке компонента плана.**
  «Собран» (Button-Toggle → `Button toggle_mob`) = числа есть в Figma, их можно снять;
  «нет» (Button-Icon) = источника нет вовсе, и это **решение владельца**, а не то, что агент
  выводит из Material — предлагать варианты с опорой на платформы и ждать ответа. Снятие чисел
  из Figma требует, чтобы пользователь переключил приложение на файл ДС и выделил нужный
  `_mob`-компонент: MCP видит только активный документ (рецепт: skill `iiko-ds-components`,
  `references/figma-mcp.md`).
- **Мобильные значения берутся только из рекомендаций платформ, без Figma.** Источник —
  первоисточники платформ: дока Material, Angular Material, HIG.
  Владелец сказал прямо: «Не надо лезть вообще в фигму…
  По мобильным компонентам мы пользуемся только теми рекомендациями что есть тут». Смотреть `_mob`-компоненты
  в Figma тоже не надо. Проверенный рецепт высоты: 40 dp = pad 10 (`--ds-space-2-5x`) + иконка/строка 20;
  тач-таргет 48 dp — отдельным слоем.
  Это правило про **числа**; **ссылку на макет экрана** владелец даёт сам («Мобери примерно вот такой
  экран» + URL узла) — тогда узел снимается через Dev Mode MCP и это не «полез в Figma за значениями»
  (рецепт — снятие узла через Dev Mode MCP).
- **Не отвечать на неоднозначную задачу только вопросами.** Если есть очевидная трактовка —
  делать по ней, перечислить допущения и указать, что менять, если формат не тот;
  ответ из одних уточнений он воспринимает как «работа не начата» и повторяет задание.
  **Исключение — вопрос про ОБЛАСТЬ правки, а не про её содержание.** Формулировать так: назвать понятую
  часть («слэш меняю на иконку прямо между числами»), затем 2–3 конкретных варианта нумерами из
  фактического состояния страницы и «скажите цифру». Принято: «Только у другого набора блюд» →
  вопрос с тремя вариантами → «Понял правильно и сделай в стеке рибай» (15.09.2026). Открытый вопрос
  «что вы имели в виду» без вариантов — нет.
- **«Подумай как улучшить и сначала предложи. Не делай» — ответ только текстом, файлы не трогать.**
  Формат, который он принял: 2–3 варианта, у каждого «что остаётся / что убирается», как читается в
  состояниях (не нажал · нажал коллега · нажал я · готово) и плюс-минус одной строкой; один помечен
  «рекомендую» с одной фразой почему; в конце короткий вопрос «какой брать». Реализация — только после его
  выбора, и то **новым блоком ниже**, а не заменой. Тот же сигнал, что и «это пока размышления»:
- **«Это пока размышления / нужно просто ответить, ничего не делать» — не править файлы.** Так он
  пробует идею: нужен разбор (что уже есть, что перенести, чего не хватает), без единой правки в репо;
  и наоборот — прежде чем предлагать свой механизм, посмотреть в наших же прототипах, не решено ли это
  уже (ревью-механику он сам указал взять из готовой страницы).
- **Строковая замена разметки на странице бьёт и по телу экрана.** `preview_html` несёт оба экрана
  одним куском: `h.replace(фрагмент, новое)` с фрагментом строки списка (иконка `receipt_long` + слот)
  сняло иконки не только в шторке Badge, а в 12 местах — вместе с телом обоих экранов (в выводе
  «убрано иконок: 12» вместо 6). После любой такой правки сверять блоки: извлечь `.phone__body`,
  `.phone__head`, `.phone__status`, `.phone__foot` из текущего файла и из `git show HEAD:<файл>` и
  сравнить — тело обязано совпасть; восстанавливать по признаку строки (у тела есть
  `ds-list-item__label-up`, у шторки нет).
- **«делай» без видимого предложения — сначала найти его в истории, потом проверить файлами.** Сессия
  может закончиться на согласии владельца, а следующая начинается с «делай» (в ACP контекст не
  переносится). Найти предложение через `session_search` — но не верить, что работа уже сделана:
  сравнить данные с `git show HEAD:<путь>` поле за полем и посмотреть время правки файлов. Так видно,
  что шторки восьми страниц всё ещё оставались заглушками, хотя предыдущая сессия закончилась на «делай».
- **Свой список предложений вести со статусом и помечать, что отвечать не надо.** Выдав список из 8 пунктов
  «что ещё полезного можно сделать», я не отметил его как предложение — и услышал «Я не понял что с твоими
  советами в итоге? На них нужно ответить или сейчас уже немного иначе все выглядит?». Отдавая список идей,
  сразу писать «отвечать не нужно» и держать таблицу «пункт → закрыт / частично / открыт → что осталось»;
  когда часть закрылась по ходу дела, обновлять статус самому.
