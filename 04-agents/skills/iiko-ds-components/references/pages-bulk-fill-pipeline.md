# Разлив формата страниц на все 38 компонентов (13.09.2026)

Задача владельца: «Давай доделаем страницы все. Итого везде на страницах нужно 4 колонка правки с
изменением значений. 3 вариант превью с разными компонентами и главное чтобы компонент главный что
исследуем тоже был. И 3 колонки с рекомендациями по главному компоненту как что где как лучше какие
опасения». Это тот же формат, что уже принят на `button.html` и `button-icon.html` — разлить на все
страницы, а не изобретать новый.

Три блока = три ключа в `data/<slug>.json` (генератор `_audit/rec/build.py` уже умеет все три):

| Блок на странице | Ключ данных | Где рисуется |
|---|---|---|
| 4-я колонка «Правка» таблицы «Что меняется на мобиле» | `changes[].edit` | `changes_table()` |
| «На экране» — 3 экрана в корпусе телефона | `preview_html` | `page()`, поле `preview` |
| «Что говорят платформы» — 3 колонки | `platform_notes_ru` + `logic_ru` | `platforms_card()` |

Ни одна из страниц не правится руками: страница — производная от `data/<slug>.json`.

## Почему партиями и через файлы-заготовки

Разлив на 37–38 компонентов нельзя делать параллельными исполнителями прямо в `data/*.json` — они
передерутся за файлы, а `build.py` соберёт кашу. Работающая схема (проверена на платформенных колонках,
36 страниц легли одним махом):

1. Общее задание пишется один раз в `_audit/rec/out/SPEC.md`: структура данных, правила, источники, что
   проверять перед сдачей. Исполнителю передаётся путь к SPEC, а не пересказ.
2. Исполнитель (агент) пишет **только** свои файлы: `out/edits/<slug>.json`, `out/previews/<slug>.json`,
   `out/platforms/<slug>.json` — один компонент = один блок = один файл. `data/`, `build.py`, `mock.py`,
   `recommendations/`, сервер и браузер трогать запрещено (это первым делом в контексте задачи).
3. Разбивка: 9 исполнителей — по 3 на блок, внутри блока по 12–13 компонентов. Платформенные колонки
   (36 страниц) так собрались за считаные минуты; полевые блоки дольше — там нужно читать CSS компонента.
4. Слияние — один скрипт `_audit/rec/apply_out.py`: переносит заготовки в `data/*.json` и сохраняет формат
   данных (`indent=1`, CRLF); с `--build` сразу вызывает `build.py`. Запуск из `_audit/rec`.

### Форматы заготовок

```json
// out/edits/<slug>.json
{"slug": "checkbox",
 "edits": [{"row": 0, "edits": [{"id": "row", "v": 48, "sel": ".ds-checkbox", "css": "min-height:@px"}]}]}

// out/previews/<slug>.json
{"slug": "checkbox", "preview_html": "<div class=\"phones\">…3 экрана…</div>"}

// out/platforms/<slug>.json
{"slug": "checkbox",
 "platform_notes_ru": [{"title": "Material Design 3", "items": ["…"]}, {"title": "iOS HIG", "items": ["…"]}],
 "logic_ru": ["…"]}
```

`row` — индекс строки в `changes`, а не `what`: строки переписываются, индекс тоже перепроверять.

## Колонка «Правка»: правило полей

Поле ставится на **каждую строку, где в колонке Mobile есть конкретное число в px** — включая строки,
где число совпадает с десктопом (`Иконка 20 → 20` на Button поле имеет: он правит размер, а не
«изменение»). Строки без числа в Mobile («те же», «на всю ширину», «по содержимому») остаются пустой
ячейкой — это правильный результат, а не недоделка. Два числа в строке (верт./гор. паддинги, `20 × 20`) —
два поля.

- `sel` обязан найтись в разметке этой же страницы (классы — в `data/<slug>.json`, `examples[].html`):
  проверять `re` по файлу данных, а не глазами; для структурных компонентов целить контейнер/строку, а не панель.
- `css` — реальные свойства, `@` = число, `@px` = число с единицей. На странице правило приезжает как
  `[data-mode="mobile"] <sel>{…}` в `<style id="live">`, который в `<head>` идёт **после** всех ссылок на CSS
  → равная специфичность решается порядком, правило выигрывает у мобильного слоя. Менять местами нельзя.
  Исключение — **inline-стиль в разметке примера**: он старше любого селектора, и поле без `!important`
  в своём `css` не работает вообще.
- `sync` — только где связь линейная и её результат виден в поле (height ↔ pad-v).
- Колонку Mobile не переписывать никогда.

## Источники текста для платформенных колонок

- `_audit/platform/<slug>.json` — есть на все компоненты плана (40 файлов): `platforms.md3/angular/apple`
  (у каждого `sizes`: name, height_dp, quote, source), плюс `not_recommended_ru`, `verdict_ru`.
- `_audit/rec/data-tech/<slug>.json` — только у 9 компонентов (button, button-icon, button-toggle, card,
  checkbox, form-field, radio, slide-toggle, stepper).
- Имя файла платформы ≠ slug: `radio` → `radio-button.json`, `hint-tooltip` → `tooltip.json`,
  `form-field` → `text-field.json`, `table-2-lvl` → `table.json`, `snackbar` → `snackbar.json` (+ `toast.json`),
  `text-ui` → ближайший. Остальные совпадают.
- В колонках — только числа из этих файлов, ссылка на файл в скобках в каждом пункте. Выгрузку на страницу
  не выводить (владелец это уже отклонял): текст пишется руками, выгрузка — источник правды.
- Заготовки этого блока цитируют «(checkbox.json)» — так же, как эталон Button, и это принимается.
- Проверено на живых страницах: 36 заготовок дали 3 колонки на **всех 38** страницах (Button и Button icon
  были раньше). Заголовки групп вышли «Material Design 3» / «iOS HIG», третью «Логика (от себя, без источника)»
  дописывает `platforms_card()`.

## Проверка после слияния

Порядок: `apply_out.py --build` → `scripts/check-page-js.py` (JS страниц не сломан) → `scripts/audit-edits.py`
→ скрин спорных страниц → отчёт.

`scripts/audit-edits.py` (лежит в `_audit/rec/checks/audit-edits.py` и в `scripts/` скилла) ходит по живым
страницам через iframe-обёртку и печатает:

| Метка | Что значит |
|---|---|
| `MISS` | селектор поля не нашёл ни одного элемента в мобильной панели или на экранах |
| `NOCHANGE` | подставили другое число (`v + 8`) — измеряемая величина не изменилась, поле бесполезно |
| `SCREENS` | экранов в блоке «На экране» не три |
| `ERR` | исключение в замере конкретной страницы |
| расхождения с данными | число полей/экранов на странице ≠ в `data/*.json`; нет блока платформ |

Псевдоэлементы (`::after` тач-слоя) обязательно мерить `getComputedStyle(el, '::after')`, а `querySelector`
получать по базе селектора — иначе поле честно работающее, но помеченное `MISS`.
Эталонный прогон: `python audit-edits.py button button-icon` → «полей: 6, экранов: 3, MISS 0, NOCHANGE 0,
расхождения 0».

### Ложный `NOCHANGE` — три источника, все в харнессе (13.09.2026)

Первый полный прогон показал 6 «мёртвых» полей; настоящими оказались два. Остальные четыре лечились в самой
проверке, и это надо помнить прежде чем «чинить» страницу:

- **Фильтр свойств.** В `props(css)` стояло `.filter(p => !/^(padding|margin)$/.test(p))` — у полей с `padding:@px`
  список измеряемых свойств становился пустым, и менялся только прямоугольник (а он у кадра с фиксированной
  высотой не двигается). Мерить **все** объявленные свойства, шорткаты не выкидывать.
- **Замер до transition.** `f.value = v; dispatchEvent('input')` и сразу `getComputedStyle` отдаёт **старое**
  значение: у Slide toggle ход ручки `transform` так и читался `matrix(1,0,0,1,20,0)` при правиле 60 px.
  Правильно — двухпроходный замер: выставить значения всем полям страницы, подождать ~700 мс, потом измерять
  и восстанавливать. Так 6 «мёртвых» превратились в один (autocomplete).
- **Псевдоэлемент.** `document.querySelector(sel + '::after')` не находит ничего → `MISS` на живом поле
  (`.ds-btn::after` на Button). Брать базу селектора для `querySelector`, а псевдоэлемент передавать вторым
  аргументом в `getComputedStyle`.

### Два настоящих мёртвых поля и их причины

- `autocomplete`, строка «Строка подсказки»: `.ds-menu-item` приходит из данных с inline
  `style="min-height:48px;width:auto"` — inline перебивает любой селектор, поэтому в `css` поля нужен
  `min-height:@px !important`. Общее правило: если свойство в разметке примера задано inline, поле без
  `!important` не сработает (и наоборот — инлайновые размеры в примерах это уже известный источник ложных
  «правило не применилось»).
- `stepper`, строка «Шаг: маркер, текст и строка»: в мобильном слое шаг задан
  `.ds-stepper.ds-stepper--vertical .ds-step { min-height: 48px }` (0,3,0), а поле целилось в
  `[data-mode="mobile"] .ds-step` (0,2,0) и проигрывало. Селектор поля повторяет селектор слоя.

### Класс, которого нет в ДС: `ds-tab--selected` (mock.py)

Валидация заготовок («каждый класс из `preview_html` есть в CSS ДС или в `rec.css`») нашла `ds-tab--selected`
в превью `menu`, `search`, `select` — и это оказалось **багом каркаса**: `mock.tabs()` рисовал выбранный таб
классом, которого в ДС нет (реальный — `ds-tab--active`, `.ds-tab--selected` не существует ни в одной CSS).
Исправлено в `mock.py` (helper) и в трёх заготовках; в старом `preview_html` у `button.json` вхождение
осталось — правится только по слову владельца. Обратная ловушка того же валидатора: `ds-select-item__text` и
`ds-input-number-but-icon--disabled` в CSS отсутствуют, но в разметке страниц есть (компонент их использует) —
«класса нет в CSS» само по себе не дефект, смотреть надо на разметку.

**Ловушка харнесса, стоившая ложного «сервер виноват».** В драйвере-обёртке нужно явно писать накопленное
в `<pre id="out">` (`flush()` после каждой страницы). Если этого нет, `--dump-dom` отдаёт пустой `<pre>`,
скрипт печатает нули по всем категориям, и это читается как «страницы не отрисовались». Симптом ровно тот
же, что у ловушки с `'\n'` в шаблонной строке (`check-page-js.py`): сначала проверять драйвер, а не сервер.

### Приёмка глазами — тоже часть проверки

Владелец смотрит страницы сам и отвечает мгновенно («Не вижу в колонке Правки чтобы можно было изменить
какие-либо значения!» — на момент, когда колонка была разлита ещё не везде). Поэтому после слияния:
снять скрин headless Chrome (`--window-size=1500,4200 --screenshot=…`) и посмотреть его vision-ом — поле,
три экрана, три колонки; дать URL одной страницы текстом и напомнить один `Ctrl+F5`.

## Как докладывать

Одним сообщением: что уже стоит на всех страницах (с URL одной страницы для проверки глазами), что в работе,
и чем проверено. Без пересказа процесса и без «я проверил» без чисел. Если после отчёта он говорит «не вижу»
— сначала выяснить, какая страница и не старая ли вкладка (`Ctrl+F5`), и только потом что-то менять.
